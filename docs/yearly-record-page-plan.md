# 年別投稿ページの影響調査・改修計画

調査・再検査日：2026-10-19。以下は実装前の調査と計画。承認後に実装・検証を完了した。現行の仕様・構成・更新手順・検証結果は [年別記録ページ](yearly-record-page.md) を参照。開発DBの変更・本番反映は行っていない。

## 確定した要件

- ページは `next/pages/date/[year].js`。
- 2015年以降はその年に投稿された記録を表示する。2014年だけ2013年以前の投稿も含める。全年度の累積一覧ではない。
- 当年の締切は取得開始時の現在時刻、過去年は12月31日23:59:59まで。日時・年の判定は既存Laravelに合わせてAsia/Tokyoとする。
- 同じ記録を年内に更新した場合は締切時点の最新記録だけを表示する。
- 通常ランキング・特殊ランキング・期間限定・RTAのボタンで切り替える。通常ランキングが初期選択。対象記録がないカテゴリは表示しない。
- 証拠動画あり／すべて表示を切り替える。初期値は動画あり。
- サイト内記録はランクポイント降順。RTAについてはユーザー確認により、種目別・タイム順とし、独自のランクポイントは導入しない。
- RTAの種目は既存speedrunページの定義に限定する。
- 過去年を長期キャッシュする。未来年・2013年以前・不正なyearは404。

## 再検査結果：既存の年別抽出を基礎にする

**既存のステージ別年フィルターと同じ意味の年末ランキングは、既存ロジックで抽出できる。** 前回は通常の新規投稿による記録更新と、既存投稿の再編集・削除を十分に分けず、完全な履歴復元を本機能の前提のように扱った点を訂正する。

呼び出しはステージページ → `/api/record/{stage}/{console}/{rule}/{year}/{difficulty}` → `RecordController::show()`。別の年末スナップショットテーブルを読み込む処理ではなく、その都度次の手順で計算している。

1. `created_at < 翌年1月1日` と `flg < 2` で候補を取得する。
2. ルールのスコア方向、created_at昇順、post_id昇順で並べる。
3. `duplicates_cleaner(..., 'user_id')` でユーザーごとの先頭、つまり年末までの自己ベストを残す。同点なら先着記録。
4. `rank_calc()` で対象年の順位・RPを計算する。

通常の新規投稿は過去の有効行を無効化しない。2024年100点、2025年200点の二つを投稿した場合、2024年指定は100点、2025年指定は200点を返す。年内に90点→120点→110点と投稿した場合は、最後の110点ではなく120点を返す。

限定的な制約として、既存投稿の再編集・削除でflg=2になった行は過去年指定でも戻らない。この挙動は既存ステージページにも共通する。無効行を戻さず、既存ページとの整合を優先する。後日の訂正・削除まで含めた完全な監査履歴復元は別要件とし、revision追加や記録書込経路の変更を本機能の必須工程から外す。

## データ処理の設計案

### サイト内記録

1. Laravelに年別専用の公開API（例：`GET /api/date/{year}`）と集計サービスを新設する。業務DBはLaravel経由とし、Prismaからrecordsを直接読まない。
2. 厳密な4桁整数かつ `2014 <= year <= 現在のJST年` を検証する。締切を処理開始時に一度確定し、取得・選別・順位・RPで共有する。
3. 順位計算用には締切までの公開可能な記録を取得する。表示対象の年だけに先に絞ると、前年以前の参加者が消えて順位・RPが変わるため、母集団と表示対象を分ける。
4. ステージ・実体ルールごとに、既存ステージページと同じ操作方法／難易度条件でユーザーごとの代表記録を選ぶ。既存のconsole=0／difficulty=0は条件内で統合し、機種・難易度別の複数行へ勝手に変更しない。大会カードは大会・カードの実体を照合する。
5. 選別は既存の「年末までの自己ベスト、同点は先着」を共用する計画へ変更する。投稿日時が最後の行を採用する独自ロジックは追加しない。ただし原要件の「最新」が低スコアの再投稿も含む最終投稿を意味する場合は既存処理と異なるため、実装前にその差だけ確認する。
6. 既存の順位・RP・参加者数の条件と一致する結果を基準に、全ステージ横断で一括計算できる共通サービスへ切り出す。ステージAPIを全件分ループで呼ぶ方式は避ける。既存のスコア方向とRP式を使用する。同点は1,1,3。RPの最大参加者数の参照範囲は通常／特殊／大会ごとに明文化し、現行の通常ランキング等と照合する。
7. 上記の代表記録から、2015年以降は当年内の投稿だけ、2014年は下限なしで抽出する。公開されていないルール48や開催中大会は除外する。
8. サイト内カテゴリ内をRP降順で安定ソートする。RP同点は投稿日時、post_idなど固定の副キーを定める。
9. 動画フィルターは代表記録・順位・RPの確定後に適用する。最新記録に動画がなく、古い記録に動画がある場合でも、古い記録へ差し戻さない。フィルターで順位・RPは再計算しない。

通常／特殊の分類は既存通常総合／特殊総合を基準に、rule20等の互換ルール、2P・TAS・実機無差別・その他rule91の扱いを分類表にする。「すべて表示」は動画条件の切り替えであり、これらの未定義ルールを黙って除外してよい根拠にはしない。分類漏れの扱いを実装前に確定する。期間限定は固定の過去大会配列ではなく、公開可能な大会・カードとの関係も使用する。

### RTA

- 既存定義のgame/categoryを使い、`GET /runs` を全ページ取得する。種目別variables、機種、NG+除外をローカルで適用する。共通game/categoryの取得は共有し、run.idで重複を排除する。
- 投稿年はrun.date（実施日）ではなくsubmittedをJSTに変換して判定する。2014年の下限なしルールも適用する。submittedがnullの旧記録は勝手な日付を補わず、年判定不能として除外件数を把握する方針とする。
- 現在verifiedかつ、verify-dateが判明する場合は締切以前のものを候補とする。当時の承認状態・削除履歴は完全には取得できないので、サイト内履歴と同様に復元限界を持つ。
- 基本案は種目・機種・プレイヤー構成単位で締切時点の自己ベストを選び、表示対象年を判定し、タイム昇順に並べる。最終投稿との違いはサイト内記録と同様に扱う。種目ヘッダーと機種表示で条件の混同を防ぐ。
- 計測値は既存ページのrealtime_tとの整合を確認する。公式順位はprimary_t基準なので、差がある種目は採用するタイムを明示する。ゲスト・複数プレイヤー・動画なしに対応する。
- プレイヤー情報はembed等でまとめ、1行ごとの外部API取得を避ける。API429・5xx・タイムアウトは部分成功を完全な一覧として保存せず、以前の正常なキャッシュを維持する。

公式仕様では `/runs` は更新前のrunも提供する一方、leaderboardsは非obsolete記録の一覧で、date条件は実施日を対象とする。投稿年を指定する条件には使えない。runsのsubmittedはnullになりうる。paginationは標準20件、最大200件なので全ページの追跡が必要。

参照：[runs](https://github.com/speedruncomorg/api/blob/master/version1/runs.md)、[leaderboards](https://github.com/speedruncomorg/api/blob/master/version1/leaderboards.md)、[pagination](https://github.com/speedruncomorg/api/blob/master/version1/pagination.md)。公式資料の確認のみで、稼働APIの互換性・取得件数・応答速度は未検証。

## 表示・キャッシュ

- ページは公開データのみをpropsに渡す。カテゴリボタン、動画フィルター、対象年・基準時刻・件数を表示する。ユーザー名は既存Prismaユーザー一覧との対応を一括解決する。
- カテゴリ有無は動画フィルター前の件数で判定する案とする。動画がないカテゴリでは「動画付き記録なし」と表示し、すべて表示へ切り替え可能にする。通常カテゴリ自体が0件なら最初の存在カテゴリへフォールバックし、全カテゴリ0件なら空表示とする。空年度は有効年なら404にしない。
- 「すべて」は全件へ到達可能とし、恣意的な50件・200件上限を設けない。大量件数ならカテゴリ単位の遅延取得／段階描画を使用し、全件propsと全行mountの負荷を計測する。
- **当年**：現在時刻の厳密性を優先してSSRとし、サイト内データは毎リクエストで取得する。RTA取得をキャッシュする場合は取得時刻と反映遅延を示し、「現在時刻までの完全即時反映」と区別する。
- **過去年**：永続的な年次データキャッシュ＋長期の再検証間隔を持つISRを候補とする。現行年はSSRなので、Pages Routerで同じファイルにgetServerSidePropsとgetStaticPropsを混在させない。実装を単純にする初期案は同ページをSSRに統一し、過去年だけ永続データキャッシュを読む方式。HTMLのISR化は必須ではない。
- 過去年データの標準再検証間隔は30日を初期案とし、通常投稿では毎回失効させない。管理訂正・削除・公開条件変更時には対象年とRP母集団への波及を踏まえて明示更新する。永久不変にはせず、失効手段を残す。
- 永続キャッシュは既存Redis等の配備設定・保持条件を確認して選定する。プロセス内Mapだけに依存しない。キーには年、仕様バージョン、カテゴリ定義・RTA定義の版、公開条件を含める。
- サイト内とRTAのデータキャッシュは分離する。同一年の生成はロック・処理共有・原子的な保存で重複取得と部分データの保存を防ぐ。上流障害は空データや404に変換しない。
- 無効なyearは外部API・DB取得前に404。未来年の404を長期保存して翌年も404にしない。JSTの年越しで現在年／過去年の判定とキャッシュ方針が切り替わることをテストする。
- 既存Recordへ年・リンクを明示指定できるpropsを追加する場合、既存画面のデフォルト挙動を維持する。過去年の記録詳細リンクは後日の編集で内容が変わりうるため、年別行は保存済みの表示データを持つ。

## 実施順序

1. 表示年の範囲・RTA並び順は確認済み。既存ステージ年別フィルターを選別基準にする。最終投稿との意味の違い、通常・特殊の対象ルール、横断取得の範囲を確定する。
2. 既存show()の年別選別・順位／RP算出を共通サービス化し、全ステージ横断の年別APIを追加する。代表記録を決めた後に表示年下限・動画条件・カテゴリ・RP順を適用する。既存show/new/totalの結果を変えない。
3. RTA年別取得・正規化・全ページ取得・永続キャッシュをサーバー側に追加する。既存の定義と除外条件を共有する。
4. `next/pages/date/[year].js`、必要な年別一覧コンポーネント、日英localeを追加する。Recordの拡張が必要ならオプションpropsで閉じる。導線追加箇所は実装時に決める。
5. 長期キャッシュ、管理者向け再生成手段、年越し処理を用意する。既存revalidate経路と整合させる。revision追加・記録書込経路の変更は本機能の必須工程に含めない。
6. 分離DB・Nodeモック・ブラウザ検証、件数／応答時間の計測を行い、必要性が確認されたindexのみ追加する。関連サマリーを実装済みの契約に合わせて更新する。

## 検証計画

- Laravel：2014年以前包含／2015年以降の年内限定、JST年末と現在時刻の境界、最新行の選別、翌年更新、同時刻、低スコア再投稿、機種・難易度・ルール分離、同点・0・RP、非公開大会、公開前rule48、近年大会分類、フィルターで順位不変。
- 履歴：削除と編集の区別がつかない既存データを復活させない。revision追加時には年末以降の編集・削除とcreated_at維持の大会更新を再現する。
