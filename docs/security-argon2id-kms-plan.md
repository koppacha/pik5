# パスワード・メール鍵のセキュリティ改修方針

決定日：2026-10-16。別セッションで実装するための引き継ぎ資料。
本書作成時点ではArgon2id・KMSとも未導入。本番の構成・AWSアクセス権限は未確認。

## 決定事項と範囲

- **Argon2idへの移行は実施する。** 新規登録と今後のログインを対象に、既存ユーザーは通常ログインの成功時に段階移行する。パスワード変更・再設定の保存処理も対象とする。
- ユーザーの追加作業、ログイン工程の追加、強制パスワード再設定・強制ログアウトは発生させない。現在の入力ポリシー変更やMFA導入は本改修の範囲外。
- **AWS KMSは、Codexが対象AWS環境を操作できる場合に導入する。** 操作可否は次セッションで確認する。利用できない場合は未実施として理由・不足権限を記録し、Argon2id改修は独立して進める。
- 今回は文書化のみ。依存追加、DB・認証情報の変更、AWS接続・リソース作成、本番反映は実施しない。
- 既存のログイン履歴・認証回数制限等は維持する。本書は[既存セキュリティ実装](security-and-rule48-implementation.md)への追加計画であり、実装済みと混同しない。

## 現状と保護対象

- 主認証はNextAuth / Prisma。Laravel業務DBとは別接続。
- パスワードはbcrypt・コスト10。`User.password`は`VARCHAR(255)`で、一般的なArgon2idのPHC文字列を格納できる。通常は列変更不要だが実装時に生成長を検証する。
- メールはAES-256-GCM、検索用`emailHash`はHMAC-SHA-256。鍵の設定名は`EMAIL_ENC_KEY_BASE64`・`EMAIL_HMAC_KEY_BASE64`。開発環境では`next/.env`に定義されている。リポジトリ直下の`.env`とは区別する。
- bcryptは復号できないが、ハッシュ単体で候補をオフライン照合できる。Argon2id移行はその計算・メモリ負担を増やす対策であり、弱いパスワードの特定を完全に防ぐものではない。
- メールは暗号文と復号鍵が揃えば復号可能。KMSの目的はファイル・DB流出と鍵の利用権限を分離すること。アプリ実行権限や平文・メモリ内の鍵まで侵害された場合の完全防御は保証しない。

## Argon2idの実装方針

### 共通処理と変更箇所

サーバー専用のパスワード処理を共通化し、ハッシュ生成・形式判定・照合・再ハッシュ要否を集約する。保存形式の識別にはbcryptの既存prefixとArgon2idのPHC prefixを使う。未対応形式や壊れた値は認証を通さず、秘密値をログへ出さない。

| 対象 | 変更 |
| --- | --- |
| `next/pages/api/auth/[...nextauth].js` | 両方式を照合し、bcryptの通常ログイン成功時に自動移行 |
| `next/pages/api/user/create.js` | 新規登録はArgon2idで保存 |
| `next/pages/api/auth/config.js` | 現在のパスワードは両方式で確認、新パスワードはArgon2idで保存 |
| `next/pages/api/auth/password-reset/confirm.js` | Argon2idで保存。既存トークンの原子的な一度限り消費を維持 |
| `next/package.json`・lockfile | 対応するArgon2ライブラリを追加し、既存bcrypt検証を維持 |
| テスト用スクリプト・その他書込経路 | パスワードの直接生成・更新を検索し、新規保存の方式を揃える |

通常の`next/prisma/seed.ts`は実ユーザー資料を読み込むため、検証目的で実行しない。旧Laravel認証は主認証と別物として依存を調査し、今回の移行で一括変更・削除しない。

### 通常ログインでの段階移行

1. 保存ハッシュの方式で照合する。失敗時には更新しない。
2. bcrypt照合が成功したら、その要求内の入力パスワードからArgon2idハッシュを作る。平文を保存・非同期ジョブへ転送しない。
3. 主キーと「照合した元ハッシュ」を条件に更新する。パスワード変更・再設定との競合で新しい値を上書きしない。
4. 条件不一致時は現在値を再確認し、変更済みパスワードに対して古い値でログインを成立させない。既に他要求が移行した場合との違いを検証する。
5. 自動移行だけの一時的な保存失敗で、正当なログインを不必要に停止させない方針とする。認証失敗・競合・DB障害を区別し、既存の障害時ポリシーと整合させる。秘密値なしの計測で再試行状況を把握する。

ログインしていないユーザーのbcryptは残る。全員の即時移行を完了条件にしない。保存ハッシュから元パスワードを復元する処理や、ハッシュだけの一括変換は実施しない。

### 互換性・負荷・切り戻し

- 現在の新規設定ポリシーは半角英数記号8〜72文字。既存ログインへ新しい登録時制限を遡及適用しない。
- 旧データに72バイト超・多バイト文字等の入力を受け入れていた可能性をコード履歴と合成データで確認する。bcryptの切捨てとArgon2idの入力解釈の違いで利用者を締め出さない。通常移行の互換性が確定しない旧ケースはbcryptのまま認証を維持し、移行処理を保留する。
- `node-argon2`等を候補とし、Node 22 / Alpineのコンテナと本番アーキテクチャでネイティブ依存を確認する。ホスト用node_modulesの流用で判断しない。
- OWASPのArgon2id最低構成（メモリ19MiB、反復2、並列度1）以上を候補に、サーバー実測で決定する。ハッシュ長・バージョン・パラメーターは明示し、同時要求数・メモリ・応答時間・認証制限との整合を確認する。
- 最初に両方式の読み取り互換性を導入し、その後Argon2idの新規保存・移行を有効にする。移行後はbcryptしか読めない旧版へ切り戻さない。移行の停止は可能にしても、ハッシュの逆変換やDBバックアップ全体の復元を通常の切り戻しに使わない。

## KMSの導入条件と設計候補

### 次セッションでの操作可否の確認

1. 利用可能なAWS連携ツールまたはAWS CLIと、安全な認証手段の有無を確認する。秘密値は表示しない。
2. 読み取り操作で接続先アカウント・リージョン・主体と権限範囲を確認する。CLIの存在やSTS照会成功だけでKMSの作成・設定権限ありと判断しない。
3. KMS鍵・鍵ポリシー・アプリ実行主体への権限設定・監査・接続元からの疎通を管理できるか確認する。既存環境への影響と有料リソースの範囲も明確にする。
4. アプリ実行環境を確認する。AWS内ならIAMロール、AWS外ならRoles Anywhere等の短期認証手段を検討し、実装方式を確定する。Codexの管理権限とアプリの実行権限は分離する。

CodexがAWSを操作できることと、本番アプリがKMSを安全に利用できることは別条件。導入方針は承認済みだが、今回は接続可否を調べていない。権限が不足する場合は不足事項を具体的に引き継ぎ、完了扱いにしない。既存鍵の削除・無効化、本番切替などの不可逆性・影響は実施時に個別に評価する。

### 最小変更の第一候補

既存のメール暗号化鍵とHMAC鍵を、KMSで暗号化して保管する。アプリは起動時等にKMSで復号し、平文鍵はメモリだけで使用する。現在のAES-GCM暗号文と`emailHash`を維持できるため、ユーザー操作やメールの再登録は不要。

- KMS鍵はカスタマー管理鍵を候補とし、鍵管理権限と利用権限を分離する。アプリには必要な鍵・操作・暗号化コンテキストに限定した権限を与える。
- `.env`等には鍵ID・リージョン・暗号化済みの鍵情報だけを置き、平文鍵やKMS復号が可能な長期AWSアクセスキーを同居させない。キーID自体は秘密鍵ではない。
- 環境ごとに鍵・実行主体を分離する。暗号化コンテキストには用途・環境等を使い、メール等の個人情報や秘密値は入れない。
- 既存鍵を包む移行では、メール全件の復号は不要。鍵を扱う処理はサーバー内で完結させ、Codexの出力・コマンド引数・一時ファイル・ソース・ログ・Gitへ平文鍵を転記しない。
- 平文鍵の旧ファイル・イメージ・バックアップの扱いを整理する。既に流出した鍵はKMSへ移すだけでは安全にならず、必要ならメール再暗号化とHMAC再計算を伴う別の鍵更新計画を作る。
- KMS鍵のローテーションと、アプリで使うデータ鍵の更新を区別する。KMSの自動ローテーションだけで既存メールの暗号鍵が置き換わるとは扱わない。

メールごとにKMSで直接暗号化・復号する方式は、鍵をアプリへ渡さずに済む一方で変更範囲が広い。現段階では採用確定ではなく、必要に応じて比較する。

### 限界・可用性・運用

- DBと設定ファイルだけの流出では、KMSの利用権限がなければ復号できない構成を目標とする。
- アプリ権限を奪われた場合のKMS悪用や、メモリ内の復号済み鍵・メールの取得は残る。取り出された鍵のコピーは、KMSを無効化しても失効できない。
- CloudTrailはKMS APIを監査する。復号済み鍵でのローカル暗号操作は記録されない。キャッシュ期間と監査の粒度を設計時に決める。
- KMS障害・権限不足・タイムアウト時の動作を、メール表示・OTP・リセット・ログインの各経路で設計する。平文保存や同梱鍵への無断フォールバックはしない。ユーザー工程を変えずに導入しても外部依存が増える点は運用上の制約として扱う。
- 料金・呼出回数・監視・権限取消・復旧手順を記録し、暗号化済みデータの復旧確認前に旧鍵を削除しない。

## 検証と完了条件

### Argon2id

- 合成パスワードで新規登録・通常ログイン・設定変更・リセットが成功し、誤入力は拒否される。
- bcryptでの初回成功時だけ移行され、以降はArgon2idで認証できる。失敗時・非ログインユーザーは変更されない。
- 同時ログインとパスワード変更・リセットの競合、壊れたハッシュ、旧入力の互換性、自動更新失敗を検証する。
- 専用テストユーザーでNextAuth経由の実経路を確認する。入力画面・工程・セッションの扱いが変わらない。
- Nodeテスト、lint、隔離したNext buildとコンテナ内の負荷確認を行う。実施結果と未実施を分けて報告する。
- 実ユーザーのハッシュ・平文・メールはテストへ流用しない。DB初期化、通常Prisma seed、実ユーザーの認証情報変更は行わない。

### KMS（導入条件成立時）

- 合成鍵・合成メールで暗号化済み鍵の取得、暗号化・復号・検索の整合を確認する。実ユーザーの復号結果を調査・表示しない。
- 権限なしの主体、異なる鍵・環境・コンテキスト、改ざん、KMS停止時の拒否・復旧を確認する。
- アプリ配布物・設定に平文鍵や長期AWS認証情報を残さず、監査・最小権限・復旧手順を確認する。
- 本番反映は実環境・バックアップ・切替対象を確認した別工程で行う。条件未成立ならKMS未導入と明記し、Argon2id完了と分ける。

## 次セッションの開始手順

1. `AGENTS.md`と[開発ドキュメントの入口](README.md)、本書、[認証サマリー](codex-summary/auth-security-proxy.md)を読む。
2. `git status --short`と現行認証コードを確認する。本書作成時点の作業ツリーには他機能の未コミット変更が多数あり、巻き戻さない。
3. Argon2idの共通処理・両方式対応・合成データのテストから着手する。
4. AWS操作可否とアプリ認証方式を確認し、条件を満たせばKMSを導入する。確認結果は秘密値を含めず記録する。
5. 実装・検証・本番反映の状態を区別し、本書とサマリーの「未導入」を実態に合わせて更新する。
