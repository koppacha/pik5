# リリース前横断検査（2026-10-09）

## 修正後の追記

2026-10-09：ユーザー指示により、R1〜R6と条件付き・低優先のコード問題を修正し、関連テスト117件、Next API26ケース、lint、Playwright、隔離MySQLの並行処理確認を完了した。[修正結果](./tricks-release-fixes-2026-10-09.md)を参照。以下の本文は修正前の検査記録であり、現行コードの状態ではない。

R7/R8は元文書を変更せず、[不整合一覧](./tricks-manual-inconsistencies-2026-10-09.md)に整理した。R7のPDF6ページの記述はRPではなく還元DPについてであり、下記の「単独投稿2R」の説明は訂正する。本番環境には未適用。

## 結論と対象

現状のままのリリースは推奨しない。大会の公平性を損なう権限境界の問題2件、投稿・削除・徴収・終了時配分の不具合、参加者向け説明の矛盾を確認した。大規模サービス向けの追加基盤を必須とはしない。まず下記の大会運用に直接影響する問題を修正する。

対象は `limited-trick` の `master` 分岐点 `97ae69afdc370daf68231886366a98c05053ae0e` → HEAD `50236f1c472f0e8cd03cdfba801a45cf1b8ea890` と、検査開始時点の未コミット変更。セキュリティ用inventoryはコミット範囲117対象、未コミット範囲59対象を全ページ取得し、Laravel・Next・運用/生成器に分担してレビューした。関連認証・設定・テスト・現在の仕様書とMarkdown/PDFマニュアルも照合した。生成ログは実行経路と形式を確認し、全シミュレーションの意味的再検証はしていない。指示に従い一般セッションログ、秘密情報、実在ユーザー認証情報は閲覧・再利用していない。ソース修正、本番操作、実DB変更はしていない。

以下のソース行は現行作業ツリー基準。正式なセキュリティ報告ではコミット範囲のHEAD行を使用している。

## 優先修正事項

### R1 / P1：予約名ユーザーIDによる未配布カードの取得・テイク

- 場所：`laravel/app/Services/Tricks/TrickGameService.php:144–146`、`TrickStateService.php:162–164,205–207`。登録側 `next/pages/api/user/create.js:31–35`。
- `_deck` は通常登録のID正規表現を通る。カードのシステム状態と所有者IDが同じ `state` に格納され、本人IDとの比較が未配布カードにも一致する。正規の本人署名であっても防げない。
- 分離SQLiteのrole 0ダミーで、ドロー前のカード2枚を手札として受信し、テイクが200、選択札がfield・他札がstackへ変わることを確認。全デッキの漏えい・消費が可能。同根の他予約名も保護が必要。
- 最小対策：参加・手札読出し・全カード操作で予約名を拒否し、既存予約名IDの有無を値を開示せず確認する。恒久対策は状態と所有者の別管理。登録APIだけの拒否では既存IDを保護できない。
- 分類：CWE-863/CWE-639、severity high。本ブランチのコミット済み変更で導入、現行にも残存。

### R2 / P2：期限後の投稿が受理され期限・順位を変更する

- 場所：`laravel/app/Services/Tricks/TrickRecordService.php:42–48,133–138`。
- 投稿は大会開催時間とfield状態を確認するが、カードの `limit_at` を確認しない。期限から毎分maintenanceの回収までの間に投稿すると有効になる。
- 分離SQLiteで期限+1秒の投稿200、初投稿による期限+1800秒を確認。回収前の順位・報酬・ホルダー候補へ影響する。
- 対策：投稿保存transaction内で期限同時刻以降を拒否し、保存を含めrollbackする。期限直前・同時刻・直後、maintenanceとの競合を確認する。
- 分類：CWE-863/CWE-841、severity medium。コミット範囲で導入、現行にも残存。

### R3 / P2：大会投稿の上限がフロントAPIだけ99,999

- 場所：`next/pages/api/server/post.js:205–211`、`next/lib/recordValidation.js`。
- フォーム・Laravel・現行ルールは999,999まで許可するが、Next投稿APIはschemaへ大会フラグを渡さず通常上限99,999を適用する。
- 実際のhandlerとvalidationを読み込む隔離テストで83は200・転送あり、999,999は400・転送なしを確認。外部依存はモックで、実ログインや実DBは使っていない。
- 対策：検証済みの大会コンテキストをschemaへ渡す。通常投稿の上限を一律緩和しない。100,000と999,999の大会投稿を含む実経路テストを追加する。

### R4 / P2：開催中の大会記録を本人・管理者も削除できない

- 場所：`next/pages/api/server/delete/[...delete].js:48–52`、`laravel/app/Http/Controllers/RecordController.php:78–84`。
- DELETE proxyが権限確認前に公開GETで記録を取得する。公開GETは開催中大会の記録を404にするため、正規の削除処理へ進めない。編集POSTのPrisma lookupとは異なる。
- ソースの処理経路から確認。ブラウザでの実ログイン削除再現は未実施。
- 対策：非公開記録も本人・管理者の権限確認に使用できる認証付き取得または安全なサーバーDB lookupへ変更する。公開範囲は維持する。

### R5 / P2：参加前の定期徴収を遡って受ける

- 場所：`laravel/app/Services/Tricks/TrickSubsidyService.php:50,90–103`。
- 給付ループは参加時刻がslotより後なら除外するが、徴収ループには同じ条件がない。遅延maintenance時に参加前slotの徴収が適用される。
- 分離SQLiteで12:05参加・12:00slot処理により残高11→10を確認。
- 対策：給付と徴収でslot参加資格を共有する。ランキングリセット徴収免除を参加前slotで消費しないことも確認する。

### R6 / P2：終了時のポット配分先が表示予測と一致しない

- 場所：`laravel/app/Services/Tricks/TrickEventFinalizer.php:38–41`。
- 通常回収は期限順だが終了時一括回収の取得順は未指定。終了時に残る複数札では、先に取得された札へポットが移る。
- 分離SQLiteで期限が早いID2の予測原資10に対し、期限が遅いID1にポット7、ID2に0となった。
- 対策：仕様で期限順と同時刻のtie-breakを明示し、予測・通常回収・終了回収の順序を統一する。

### R7 / P2：表示PDFの給付・徴収・終了前ルールが現行と異なる

- 画面が表示する `next/public/limited/tricks/limited_19_manual.pdf` を11ページ確認し、該当ページをレンダリング確認した。
- PDF8ページ：定期給付は「手札+Pが8以下」、緊急補充は全員「3以下」、徴収判定は「手札+P」。現行は定期給付 `<3`、緊急補充の全員条件 `<3`、徴収はDP残高だけが閾値を超える場合。
- PDF9ページ：終了1時間前以降は給付・徴収も停止と説明するが、現行処理は大会終了まで続く。
- PDF6ページの「最下位は常に0」も現行RP配分と一致しない。例えば単独投稿は2R。
- 対策：運営が採用する現行ルールを確定し、画面から実際に開くPDFとMarkdownを統一する。旧PDFの保管方針と現在の表示導線を分ける。

### R8 / P2：テイク前の練習記録を投稿できるか説明が矛盾

- `docs/tricks-rules.md:137–139` は無制限の手札練習と「練習成果はテイク後のスコア投稿に利用できる」と記載。
- `next/pages/keyword/tricks-manual.md:93` は練習記録の温存投稿を禁止し、投稿可能後にプレイした記録だけを許可。
- 「成果」が技術・知識だけを意味するのか記録自体も含むのか、現状では参加者が判断できない。Webシステムにオフラインプレイ日時の検証はない。
- 対策：運営判断を一本化し、記録の持越し可否を両文書で明記する。文言解釈で実装変更は行っていない。

## 条件付き・低優先事項

- staging編集/削除：`post.js:169–177`、DELETE `:54–62` はグローバル大会設定と1001〜1999のstage範囲で判定し、締切後404にする。他大会の記録にも影響し得る。新規投稿/参加はevent単位へ改善済みだがこの経路は残る。実環境の設定値は読んでいないため発生条件の確認が必要。
- タイム投稿ログ：`TricksHud.js:61–62` はscoreに「点」を付け、83秒を83点と表示する。タイム種別に応じて共通Score表現を使う。
- 初期化CLIの説明は200枚、実装定数は160枚。ヘルプを現行仕様へ合わせる。
- 複数大会の同時初回テイク：stage allocatorは大会別ロックの下でグローバルstage最小未使用番号を探す。単一大会は直列化されるが大会間競合の専用検証・共通ロックは未確認。複数大会並行運用をしない場合は当面の優先度が低い。
- タイム判定・短い順の順位・整数秒保持は関連テストを含め確認済み。ただし本番カードのscore_type設定、追加migration適用、既存割当stageとの整合は本番データを確認していないためリリース作業で別途確認が必要。
