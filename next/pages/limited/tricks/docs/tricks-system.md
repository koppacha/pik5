# 期間限定ランキング・トリックテイキング制 UI設計書

対象：期間限定ランキング・トリックテイキング制（Next.js + Laravel + Phaser 4）
目的：`tricks-rules.md`をUI/UXとAPI/DB仕様に落とし込み、実装可能な粒度まで確定する。

---

## 1. 前提条件

- 勝者は大会終了時の合計ランクポイント最大者とし、イベントランキングは合計ランクポイント降順で表示する
- ポイント・手札の終了時保有量は勝敗や報酬に使用せず、ミニゲームの成績をイベントの主目的とする
- 腕前差によって上位を取りにくい参加者にも、多数投稿、長時間練習、巨大スタックなど別の遊び方を提供する
- 「トリックテイキング」はメインプロジェクト配下に単一ページで表示する子プロジェクト（特設ページ）である
- この子プロジェクトは`/next/pages/limited/tricks/`に単一ページとして表示する
- ルールの正本は`next/pages/limited/tricks/docs/tricks-rules.md`とし、本ドキュメントはUI・DB・APIへの落とし込みを担当する
- シミュレーション固有の仮定・行動モデル・未採用候補は`next/pages/limited/tricks/docs/tricks-simulation.md`を正本とする
- 既存の投稿UIは`next/components/modal/RecordForm.js`を利用し、ランキング表示は`next/components/record/Record.js`をmini表示で利用する
- イベント専用のドメイン処理は共通サービスへ集約し、`TrickController.php`と汎用記録処理の双方から同じサービスを利用する
- 即時反映は短周期ポーリングを前提とする。ポーリングで大会運営上の遅延・負荷が問題になる場合にのみ、WebSocketまたはSSEを追加検討する

---

## 2. 画面構成

- canvasは画面いっぱいに表示する（既存のレイアウト制限は無視し、グローバルヘッダー以外表示しない）

### 2.1 サイト名等

- 左上固定表示
- サイト名、大会名、ログ、大会残り時間を表示する
- ログは最大10行までとし、100行までスクロールできる。101行目以降は取得しない
- ログはバックエンドを短周期ポーリングで監視して反映する
- サイト名をクリックでサイトトップページ`/next/pages/index.js`に遷移する

### 2.2 ダッシュボード

- 中央上・右固定表示（サイト名等とあわせてヘッダーを構成）
- 全参加者のプレイヤー名、ポイント、手札枚数、合計ランクポイントが合計ランクポイント降順に一覧表示
- 合計ランクポイントは「回収済みカードの確定分 + 現在の場札の暫定分」とし、投稿・更新による順位変動を短周期ポーリングまたは投稿直後の再取得で反映する
- 確定ランクポイント、暫定ランクポイント、合計ランクポイントを区別して確認できるようにする
- 一度に表示できるのは10人までとし、11位以下はスクロールして表示する
- ダッシュボードの内容はバックエンドを短周期ポーリングで監視して反映する

### 2.3 場札

- 中央表示（**スクロール可能領域。**ヘッダー・フッター以外のすべての表示領域を占有）
- 場札のカードコンポーネントを残り時間が少ない順に左上から右下に向かって表示
- テイク時点でリミットオーバー時間を必ず設定する。未設定の場札は不整合として操作せず再取得する

### 2.4 山札

- 左下固定表示
- カード裏面と「ドロー」ボタン、山札の残り枚数を表示
- ドローボタンはユーザーのポイントが0P以下のとき非活性にし、APIを発火できないようにする

### 2.5 手札

- 中央下・右固定表示（山札と手札でフッターを構成）
- 手札のカードコンポーネントをドローした順に左から表示する
- 人間が手に持っているように扇状に配置し、各カードコンポーネントは常に全域表示する必要はない
- 可能ならドラッグで並び替えできるようにする
- 手札詳細ではルールを確認してオフライン練習できるが、練習専用ボタン、練習時間、練習回数はWebシステムへ保存しない

### 2.6 捨て札

- 左下の山札付近へ捨て札枚数だけを表示し、カード内容は表示しない
- 大会終了後は山札・手札とともに非表示にする

## 3. 各コンポーネントの動作処理

### 3.1 手札クリック時の動作

- 選んだ手札を全体像が確認できる位置へ移動し、「テイク」「キャンセル」ボタンを表示する
- テイク条件を満たさない場合はテイクボタンを非活性にし、理由を表示する
    - 固定クールダウン中は、次にテイクできる時刻と残り時間を理由として表示する
- キャンセルボタンかモーダル外領域をクリックすると手札は元の位置に戻る

### 3.2 テイクボタンクリック時の動作

- 「手札をすべて消費してこのカードを場に出しますか？」という確認モーダルを表示（はい/キャンセル）
- 確認モーダルで「はい」を押下すると確認モーダルと手札モーダルを閉じ、テイクAPIを呼ぶ
- テイク成功後、選んだカードを場札として表示する
    - 手札から場札の領域へシームレスに移動する
    - 場札を公開し、テイク時点から90分後をリミットオーバー時間としてセットする
- 残りの手札はすべてスタックになり、手札からは消滅する
- テイク成功時、給付金フラグを次の給付金タイミングに対して有効化する

### 3.3 場札クリック時の動作

- 選んだ場札のカードコンポーネントと、そのゲームに投稿されたスコアがモーダル表示される（場札モーダル）
- 場札モーダルの各スコアは汎用記録コンポーネント（`next/components/record/Record`）をminiフラグをONにして表示する
    - RPS表示領域には「参加者数 - 順位 + 1」を表示し、1位にはさらに1Rを加算する
- ランキングの上部に投稿ボタンを表示し、クリックすると投稿モーダル（`next/components/modal/RecordForm`）を表示し、そのゲームへのスコアを投稿できる
- 投稿ボタン付近には、現在の参加者数を基準に算出した初投稿時の消費ポイント数を表示する。2・3人目は0P、1人目および4人目以降は場札のレア度と同値とする
- 同じプレイヤーがその場札へ既に参加済みの場合は、再投稿時のポイント消費がないことを表示する

### 3.4 スコア投稿成功時の動作

- 該当カードのリミットオーバー時間はテイク時に設定済みであることを前提とする
- 各場札の1人目および4人目以降の参加者は初投稿時にレア度と同じポイントを消費し、2・3人目は消費しない
- 投稿によるポイント消費は、所持ポイントが0P以下でも許可する
- 場札の1人目の初投稿は延長しない。2人目は60分、3人目は55分と参加順ごとに5分ずつ逓減し、13人目以降は下限5分延長する。ポイント消費の有無にかかわらず延長し、同じプレイヤーのスコア更新は延長しない
- 大会終了1時間前以降は延長しない
- 投稿成功時、給付金フラグを次の給付金タイミングに対して有効化する
- 各プレイヤーの合計ランクポイントを再計算する

### 3.5 未参加者のアクセス時の動作

- ダッシュボードに記載されていないユーザーが大会時間内にページへアクセスした場合、参加モーダルを強制ポップアップする（大会時間外の場合、参加ボタンは非活性にする）
- ログインしている場合：参加モーダルには参加ボタンとキャンセル（観戦）ボタンを配置し、参加ボタンを押下するとダッシュボードに名前が並び、5Pを得る
- 参加時の自動ドローは行わない
- 一度参加したユーザーは退出できない。ログアウトやページ離脱をしても参加状態は維持する
- ログインしていない場合：「このイベントに参加するにはログインが必要です」と表示し、ログイン画面へのリンクとキャンセルボタンを配置する
- キャンセルボタンを押すとモーダルを閉じ、ヘッダーに再度参加モーダルを表示するための「参加」ボタンを表示する（このボタンは参加モーダルでキャンセルボタンを押し、引き続き未参加の場合のみ表示する）

### 3.6 特殊な動作

- 各場札はクライアント側で毎秒表示更新する。リミットオーバー時間を過ぎた場札があれば、短周期ポーリングまたは明示API呼び出しにより回収処理を反映する
- テイク済み場札のリミットオーバー時間は必須とし、未設定の場合は不整合として操作を止め、サーバー状態を再取得する
- 大会残り時間が0になった場合、すべてのボタンを非活性にし、その大会の回収カード一覧を表示する
- 回収カードにはホルダー名または「ホルダーなし」を表示し、ホルダーありは再登場しないこと、ホルダーなしは次回イベントの山札へ戻ることを区別して表示する
- 回収カードのランキングは`event_id`と`event_card_id`で対象大会を固定し、同じ`stage_id`を使った他大会の投稿を混在させない
- 場札が0枚の場合、給付金タイミングごとに、所持ポイント5P以下の全プレイヤーへ1P給付する

### 3.7 Phaser/Reactの責務分離

- ゲーム状態の正本はLaravel APIのスナップショットとし、Phaser Sceneは描画・入力・Tween・パーティクルのアダプタとして扱う
- レンダラー非依存の判定や整形（期限切れ判定、残り時間表示、手札順、場札順、短縮表示など）は`next/lib/tricks/index.js`に置く
- Phaser canvasはカード操作と視覚演出を担当する。具体的には、手札扇形配置、ドラッグ中断時の座標復帰、山札→手札、手札→場札、場札選択時の座標移動、パーティクルを扱う
- ログ、ダッシュボード、ランキング、投稿フォームなど、スクロールやテキスト密度が高いUIはDOM/React側で扱う
- 場札詳細はPhaser側で選択カードをモーダル表示位置へ移動させ、その後React/MUIのモーダルでランキングと投稿導線を表示する

### 3.8 レンダリング負荷に関する制約

- 本イベントは低スペックPCの参加者も想定するため、見栄えのために過剰なローカルリソースを消費してはならない。フルスクリーンcanvasを使う場合でも、静的な状態で高fps描画を続ける、重いフィルターや大量パーティクルを常用する、不要に大きい描画領域を維持する実装は避ける
- Phaser Sceneの再描画では、古いGameObject、Tween、イベントリスナー、DOM要素を確実に破棄する。`children.removeAll()`のように表示リストから外すだけの処理に依存せず、必要に応じて`destroy()`やTween停止を明示する
- ポーリングやSWR更新で画面全体を再生成する場合は、更新頻度を必要最小限にする。回収・投稿・テイクなど状態変化が発生した時は即時再取得してよいが、状態変化のない監視処理で毎秒全再描画を誘発しない
- レンダリングに関わる改修をした場合は、Playwrightでcanvasが描画されることだけでなく、常時描画fps、オブジェクト数の増加、ポーリング間隔、画面を開いたままにした時のCPU/GPU負荷を確認する
- デバッグ・テスト時は`window.__TRICKS_DEBUG_SNAPSHOT__()`からGameObject、DOMカード、canvas、timer、RAF、state取得、実再描画の件数を読み取り、静止前後で増加していないことを確認できるようにする
- 過負荷または過負荷になりうる実装を検知した場合は、仕様・要件の範囲内で軽量化を優先する

## 4. コンポーネントの詳細仕様

### 4.1 カードコンポーネント

- 固定の大きさで表示する
- カード名、ルール名、ルール詳細、作成者、テイカー、難易度（★1〜★5）、レア度（1〜5）、スタック数、残り時間を表示
- カードの縁でレア度を表現する。コモン〜アンコモンはモノクロ、レアは有色、エピックはグラデーション、レジェンダリーはグラデーションのアニメーション
- 初投稿コストはレア度と同じ値として扱う
- 回収カード表示ではホルダー名または「ホルダーなし」と、次回イベントへの再登場可否を表示する

## 5. バックエンドの仕様

### 5.1 データベース

- `decks`テーブルはイベントをまたいで存続するカード本体と、カード固有の`stage_id`を管理する
- イベント内の山札・手札・場札・スタック・捨て札・回収済み状態は、`event_id`とカードを組み合わせた`trick_event_cards`で管理する
- ゲームの記録は`records`テーブルを利用する（非イベント時も使う汎用記録テーブル）
- `records`へのカラム追加はしない想定。必要な場合ユーザーの承認を要する
- 大会期間、進行状態、デバッグ時計は`trick_events`でイベント単位に管理する
- 各カードにはカード固有IDとして`card_id`を付与する。`stage_id`は投稿先となる`stages.stage_id`であり、テイクされた時点で初めて払い出す
- 既存migrationには`eventId`、`stageId`、`ruleName`、`topPlayer`などcamelCaseカラムが存在する。`stageId`は元ステージ番号として扱い、追加カラムでは`origin_stage_id`へ寄せる
- ポイント消費履歴、回収時配分履歴、ホルダー、イベント投稿との紐付け、給付金フラグは、イベント単位の冪等性を担保できる永続データとして保存する

### 5.1.1 `trick_events`テーブル設計

大会設定と進行状態を管理する。通常大会は実時刻、デバッグ・テスト大会だけは制御時計を利用できる。

| カラム                         | 型                             | 必須 | 用途 |
|-----------------------------|-------------------------------|----|------|
| `id`                        | unsigned big integer          | 必須 | 主キー |
| `event_id`                  | unsigned integer              | 必須 | 大会ID。一意制約を付ける |
| `title`                     | string                        | 必須 | 大会名 |
| `start_at` / `end_at`       | datetime                      | 必須 | 48時間の開催期間 |
| `state`                     | string                        | 必須 | `scheduled`、`active`、`ended` |
| `debug`                     | boolean                       | 必須 | デバッグ大会か |
| `test_mode`                 | boolean                       | 必須 | 自動テスト専用大会か |
| `debug_now`                 | datetime nullable             | 任意 | 停止・変更可能な大会内時刻。通常大会では参照しない |
| `last_subsidy_slot_at`      | datetime nullable             | 任意 | 大会全体で最後に処理した給付スロット。同一スロットの再処理を防ぐ |
| `random_seed`               | unsigned big integer nullable | 任意 | テスト時の抽選再現用seed |
| `initialized_at` / `ended_at` | datetime nullable           | 任意 | 初期化・終了処理の冪等性判定 |
| `created_at` / `updated_at` | timestamp                     | 必須 | Laravel標準タイムスタンプ |

- 大会時刻の取得は`TrickClock`へ集約し、通常大会では実時刻、`debug`または`test_mode`の大会だけは`debug_now`を使用する
- テストごとに一意な`event_id`を作成し、時刻操作やfixtureが他大会へ影響しないようにする

### 5.1.2 `decks`テーブル設計

`decks`はイベントをまたいで存続するカード本体を管理する。イベント内状態は`trick_event_cards`へ分離し、`stage_id`は一度付与したら変更・削除しない。

| カラム                         | 型                             | 必須 | 用途                                                                 |
|-----------------------------|-------------------------------|----|--------------------------------------------------------------------|
| `id`                        | unsigned big integer          | 必須 | カードID。内部操作の主キー                                                     |
| `card_id`                   | unsigned big integer          | 必須 | イベントをまたいでカードを識別する固有ID                                               |
| `event_id`                  | unsigned integer nullable     | 任意 | 既存`eventId`互換用。イベント履歴の正規データには使用せず、必要なら直近採用大会を保持する             |
| `stage_id`                  | unsigned integer nullable     | 任意 | 初回テイク時だけ払い出す永続的な投稿用ステージ番号。次回イベントでも同じ値を使う                    |
| `origin_stage_id`           | unsigned integer nullable     | 任意 | カードの元になった既存ステージ番号。既存`stageId`相当                                    |
| `title`                     | string                        | 必須 | カード名・ステージ名                                                         |
| `rule_name`                 | string                        | 必須 | 縛りルール名。既存`ruleName`相当                                              |
| `text`                      | text                          | 必須 | ミニゲームのルール本文                                                        |
| `state`                     | string                        | 必須 | グローバル状態。`_eligible`（投入可能）、`_in_event`（開催中大会で使用中）、`_held`（ホルダー所有） |
| `creator`                   | string nullable               | 任意 | 考案者のユーザーIDまたは表示名                                                   |
| `created_at` / `updated_at` | timestamp                     | 必須 | Laravel標準タイムスタンプ                                                   |

既存の`difficulty`、`rarity`、`taker`、`topPlayer`、`count`、`rewards`等を互換キャッシュとして残す場合でも、複数イベントの履歴判定には使用しない。正規データはカード本体を`decks`、大会内状態を`trick_event_cards`から取得する。

### 5.1.3 `trick_event_cards`テーブル設計

カードの大会内状態と大会ごとの結果を管理する。大会開始時、山札へ採用する各カードについて1行作成し、`event_id`と`deck_id`をユニークにする。

| カラム                         | 型                             | 必須 | 用途                                                                 |
|-----------------------------|-------------------------------|----|--------------------------------------------------------------------|
| `id`                        | unsigned big integer          | 必須 | 大会内カードID                                                          |
| `event_id`                  | unsigned integer              | 必須 | 大会ID                                                               |
| `deck_id`                   | unsigned big integer          | 必須 | カード本体`decks.id`                                                    |
| `state`                     | string                        | 必須 | `_deck`、`_field`、`_stack`、`_trash`、`_collected`、または手札所有者の`user_id` |
| `difficulty`                | unsigned tiny integer         | 必須 | 当該大会・ドローで使用する難易度1-5                                             |
| `rarity`                    | unsigned tiny integer nullable | 任意 | 未ドロー時null、ドロー時に付与するレア度1-5                                        |
| `stack_count`               | unsigned integer              | 必須 | テイク時点の手札枚数S                                                     |
| `taker`                     | string nullable               | 任意 | 当該大会のテイカー                                                        |
| `top_player`                | string nullable               | 任意 | 当該大会の現在トップ。共同1位の正規データは投稿集計から求める                                  |
| `post_count`                | unsigned integer              | 必須 | 当該大会の有効投稿数                                                       |
| `paid_points_total`         | integer                       | 必須 | 当該大会で支払われた初投稿ポイント総数                                             |
| `limit_at`                  | datetime nullable             | 任意 | テイク時に90分後を設定し、初投稿で延長する期限                                        |
| `taken_at`                  | datetime nullable             | 任意 | 当該大会でテイクされた時刻                                                   |
| `collected_at`              | datetime nullable             | 任意 | 当該大会で回収された時刻                                                    |
| `stack_parent_id`           | unsigned big integer nullable | 任意 | `_stack`行が紐づく親`trick_event_cards.id`                                |
| `drawn_order`               | unsigned integer nullable     | 任意 | 手札内の表示順                                                           |
| `created_at` / `updated_at` | timestamp                     | 必須 | Laravel標準タイムスタンプ                                                   |

状態値の定義は以下とする。

| state        | 意味                         |
|--------------|----------------------------|
| `_deck`      | 山札                         |
| `{user_id}`  | 指定ユーザーの手札                  |
| `_field`     | 場札。投稿可能または初回投稿待ち           |
| `_stack`     | 場札に紐づくスタックカード。他ユーザーには内容非公開 |
| `_trash`     | 捨て札。山札枯渇時の再シャッフル対象         |
| `_collected` | 回収済みカード。当該大会中は循環へ戻さず、大会終了後の結果表示に使用する |

### 5.1.4 `players`テーブル設計

### 5.1.5 `trick_card_payments`テーブル設計

プレイヤー×場札ごとの初投稿コスト支払い履歴を管理する。投稿削除後も履歴を保持し、再投稿時の二重消費を防ぐ。

| カラム                         | 型                             | 必須 | 用途                    |
|-----------------------------|-------------------------------|----|-----------------------|
| `id`                        | unsigned big integer          | 必須 | 主キー                   |
| `event_id`                  | unsigned integer              | 必須 | 支払いが発生した大会ID          |
| `event_card_id`             | unsigned big integer          | 必須 | 対象`trick_event_cards.id` |
| `deck_id`                   | unsigned big integer          | 必須 | 対象場札                  |
| `stage_id`                  | unsigned integer              | 必須 | 投稿用ステージ番号             |
| `player_name`               | string                        | 必須 | 支払ったユーザーID            |
| `points_paid`               | integer                       | 必須 | 実際に支払ったポイント。通常は場札のレア度 |
| `record_id`                 | unsigned big integer nullable | 任意 | 初回支払いの契機になった投稿ID      |
| `created_at` / `updated_at` | timestamp                     | 必須 | Laravel標準タイムスタンプ      |

- `event_id`、`deck_id`、`player_name`をユニークにし、バックエンドAPIでも同一大会・同一カード内の二重消費を防ぐ
- 同じカードが次回イベントへ再登場した場合は、前回イベントの支払い履歴を参照せず、新しい`event_id`で初投稿コストを判定する
- 同一ユーザーによる同時投稿が発生しても、支払い履歴は1件だけ作成する

### 5.1.6 `trick_collection_rewards`テーブル設計

| `id`                        | unsigned big integer | 必須 | 主キー                                       |
| `event_id`                  | unsigned integer     | 必須 | 配分が発生した大会ID                               |
| `event_card_id`             | unsigned big integer | 必須 | 対象`trick_event_cards.id`                    |
| `deck_id`                   | unsigned big integer | 必須 | 回収対象場札                                    |
| `player_name`               | string               | 必須 | ポイントを受け取るユーザーID                           |
| `points_delta`              | integer              | 必須 | 加算ポイント                                    |
| `reward_type`               | string               | 必須 | `single_poster`、`rank_distribution`、`taker_remainder` |
| `created_at` / `updated_at` | timestamp            | 必須 | Laravel標準タイムスタンプ                          |

- `event_id`、`deck_id`、`player_name`、`reward_type`の組み合わせを重複させない
- 回収APIが再実行されても、既存配分を再加算しない

### 5.1.7 `records`テーブルと`trick_event_records`の扱い

- スコア投稿は既存の汎用`records`テーブルを利用する
- `records`へのカラム追加は行わず、イベント投稿の大会帰属は中間テーブル`trick_event_records`で管理する
- `trick_event_records`は`record_id`、`event_id`、`event_card_id`、`deck_id`とタイムスタンプを保持し、`record_id`をユニークにする
- 投稿受付時は`records.stage_id = decks.stage_id`を確認したうえで、現在`_field`の`trick_event_cards`行へ紐付ける
- ランキング、参加順、暫定ランクP、回収結果は`stage_id`だけで集計せず、必ず`trick_event_records.event_id`と`event_card_id`で対象大会を限定する
- 同じ`stage_id`を次回イベントで再利用しても、前回イベントの記録は次回ランキングへ混入しない
- イベント専用ステージ番号の投稿は新着記録APIやピックアップ動画選出から除外する
- 記録の作成・編集・削除は汎用記録処理からイベント用ドメインサービスを呼び、記録更新とイベント副作用を同じサーバー処理内で一貫して実行する
- 投稿削除で有効記録が0件になったプレイヤーは現在ランキングと参加者数から外す。ただし初投稿順、0Pを含む支払い履歴、発生済み延長は保持し、再投稿時に再消費・再延長しない

### 5.1.8 `trick_card_holders`テーブル設計

ホルダーの所有権をイベント終了後も保存する。`event_id`、`deck_id`、`player_name`を保持し、共同1位の場合はプレイヤーごとに1行作成する。

| カラム                         | 型                    | 必須 | 用途                         |
|-----------------------------|----------------------|----|----------------------------|
| `id`                        | unsigned big integer | 必須 | 主キー                        |
| `event_id`                  | unsigned integer     | 必須 | ホルダーを獲得した大会ID             |
| `event_card_id`             | unsigned big integer | 必須 | 回収された`trick_event_cards.id` |
| `deck_id`                   | unsigned big integer | 必須 | 所有対象のカード本体                 |
| `player_name`               | string               | 必須 | ホルダーのユーザーID                |
| `created_at` / `updated_at` | timestamp            | 必須 | Laravel標準タイムスタンプ            |

- 回収時に1位グループ全員を登録する
- 投稿者0人の場合は行を作成しない
- `event_id`、`deck_id`、`player_name`をユニークにし、回収再実行で重複作成しない
- 1件以上存在するカードは`decks.state = '_held'`とし、以後のイベントの山札候補から除外する。管理者復帰機能は初期実装に含めない
- ホルダーなしカードは大会終了時に`decks.state = '_eligible'`へ戻し、付与済み`stage_id`を保持したまま次回イベントへ必ず投入する

### 5.1.9 `limit_logs`テーブル設計

行動ログと監査ログには既存の`limit_logs`相当のログテーブルを利用する。

| カラム                                             | 用途                                                                               |
|-------------------------------------------------|----------------------------------------------------------------------------------|

| `card_id` / `stage_id`                          | 対象カード                                                                            |

### 5.2 状態変更時のバックエンド処理

- 以下に該当する場合、または類似操作時は、現在大会の`trick_event_cards.state`を更新する
    - ドローされたとき（山札→誰かの手札）
    - テイクされたとき（誰かの手札→場札またはスタック）
    - 回収されたとき（場札→回収済み、スタック→捨て札）
- 同時アクセスに備え、参加・ドロー・テイク・投稿後更新・回収・給付金処理はDBトランザクション内で処理し、対象の`players`、`decks`、`trick_event_cards`行をロックする
- ポーリングで取得する状態は、サーバー側で正規化したスナップショットとして返す。クライアントは楽観的に確定状態を書き換えず、API応答または次回ポーリングで同期する

#### 5.2.1 大会開始・終了時のカード処理

- 大会開始時は、直前大会でホルダーなしとなった回収カードをすべて優先して含め、残りを`decks.state = '_eligible'`の他カードから補って200枚を選ぶ。同一トランザクションで`decks.state = '_in_event'`へ変更し、当該`event_id`の`trick_event_cards`を`state = '_deck'`で作成する
- `_eligible`が200枚未満の場合は大会初期化を失敗させ、不足した状態で開始したり`_held`カードを暗黙に補充したりしない
- `decks.state = '_held'`のカードは、以後のイベントの山札候補から除外する
- 大会内の状態遷移と結果表示は`trick_event_cards`に保持し、大会終了後も過去行を削除・再利用しない
- 回収カードにホルダーが1人以上いる場合は`trick_card_holders`を作成し、カード本体を`decks.state = '_held'`にする
- 投稿者0人でホルダーが存在しない回収カードは、大会終了時にカード本体を`decks.state = '_eligible'`へ戻し、次回イベントの山札へ必ず含める
- 大会終了時、ホルダーを得なかった山札・手札・捨て札・スタック等のカード本体も`_in_event`から`_eligible`へ戻す
- ホルダーなしカードを次回イベントへ投入するときは新しい`trick_event_cards`行を作成するが、`decks.stage_id`は既存値を保持する
- 過去大会の`trick_event_cards`、`trick_event_records`、支払い、配分、ログは結果表示・監査用に保持し、次回大会の集計へ混ぜない

### 5.3 参加時のバックエンド処理

- `players`に対象ユーザーが存在しない場合のみ、参加者として作成する
- 新規参加者には5Pを付与する
- 新規参加者本人には後発参加ボーナスを付与しない
- 既存参加者全員へ、後発参加ボーナスとして1Pを付与する
- 同一ユーザーの重複参加を防ぐため、`players`の`event_id`と`name`をユニークにする
- ログアウトやページ離脱では`players`行を削除しない

### 5.4 ドロー時のバックエンド処理

- 大会開始時に山札を200枚用意する
- ポイントが0P以下の場合はドローを拒否する
- まず、以下の確率分布に従ってレア度抽選を行う
    - コモン(C1)：90%、アンコモン(U2)：6%、レア(R3)：3%、エピック(E4)：0.9%、レジェンダリー(L5)：0.1%
    - 経過`t`時間におけるU2以上の確率を`min(100, 10 × 10^(t / 46))%`とし、その増加分だけC1を減らす
    - 46時間経過時を補正のピークとし、U2以上100%、C1 0%を上限とする
    - U2以上の内訳は初期比率`6：3：0.9：0.1`を維持する
- 次に、以下の確率分布に従って難易度抽選を行う
    - ★1：54%、★2：30%、★3：10%、★4：5%、★5：1%
    - 抽選前に現在大会の`trick_event_cards`の山札を調べ、山札に1枚もない難易度が1つ以上存在する場合は、その確率の合計を存在する難易度のうちもっとも低い難易度に上乗せする
- 抽選後、現在大会の山札にある該当難易度の`trick_event_cards`をランダムに1枚決定し、その大会内カードのレア度を抽選結果へ更新し、`state`をドローしたプレイヤーにする（＝手札として扱う）
- ドロー前に山札が空の場合、`_trash`のカードを`_deck`へ戻してシャッフル対象にする
- ドロー成功時はプレイヤーのポイントを1減算し、`players.card_count`を現在大会の`trick_event_cards`実数に同期する

### 5.5 テイク時のバックエンド処理

- まず、テイクできるか判定する
- テイクできる場合、現在大会の手札に対応する`trick_event_cards.state`を切り替える（選んだ手札は場札として、それ以外はスタックとして扱う）
- サーバー側でも必ず以下を検証する
    - 対象カードが操作ユーザーの手札である
    - 操作ユーザーの手札が`3 + テイク直前の場札数`枚以上
    - 大会終了1時間前より前
    - テイク後の場札数が`min(max(1, 累計参加者数 - 1), 16)`以下
    - `players.last_take_at`がnull、または現在時刻が`last_take_at + 90分`以降
- テイク成功時は、場札の`taken_at`と同じ時刻を`players.last_take_at`へ保存する
- クールダウン終了時刻は`last_take_at + 90分`とし、場札への投稿、期限延長、早期回収、通常回収では変更しない
- 同時テイクによるクールダウンすり抜けを防ぐため、条件判定から`last_take_at`更新まで操作ユーザーの`players`行を同一トランザクション内でロックする

#### 5.5.1 シミュレーション上の締切直前行動

- 大会開始から47時間経過するとテイク不能になるため、シミュレーションではその直前（46時間59分59秒999999）に全参加者がテイクを試行する
- 必要手札枚数未満または場札上限などの条件でテイクできない場合は、試行結果と理由をログへ記録する
- 複数人の試行順による固定的な有利不利を避けるため、試行順は乱数シードに基づいてシャッフルする
- テイク締切後は、新たなドローと手札練習を行動候補から除外し、残り時間を場札への初回投稿・更新に使う
- テイクするカードは手札内の練習時間を優先して選び、同条件では無作為に選ぶ。レア度そのものは選択理由に使用しない
- 参加者数は、その大会に一度でも参加した累計参加者数とする
- 選択した`trick_event_cards`行は`state = '_field'`、`taker = user_id`、`stack_count = テイク直前の手札枚数`、`taken_at = 現在時刻`、`paid_points_total = 0`に更新する
- 対応する`decks.stage_id`が未設定の場合だけ、イベント用ステージ番号を1313から順に払い出し、`stages`へステージ情報を作成して永続保存する。設定済みの場合は新規発行せず既存値を使用する
- 今回イベントの`stages`作成値は、`stage_sub = "期間限定チャレンジ"`、`type = "stage"`、`display = "int"`、`parent = 260704`、`series = origin_stage_idの先頭1桁`、`time/treasure/pikmin/border1-4 = 0`とする
- 選択されなかった`trick_event_cards`の手札行は`state = '_stack'`、`stack_parent_id = 選択した大会内カードID`に更新する
- テイク時点で`limit_at = 現在時刻 + 90分`を設定し、初投稿のない場札も90分後に回収する
- テイク成功時、次の給付金タイミングのフラグを有効化する

### 5.6 記録投稿時のバックエンド処理

- 投稿された記録はカード本体の`stage_id`を使って記録投稿処理を行う。未発行カードは初回テイク時に払い出し、再登場カードは既存値を使う
- このイベントで投稿された記録は新着記録API（`/api/new`）では取得しない（ピックアップ動画選出ロジックでも対象外になる想定）
- 投稿成功後、`records.stage_id = decks.stage_id`を満たし、かつ現在大会で`state = '_field'`の`trick_event_cards`を取得する。作成した`record_id`を`trick_event_records`へ紐付けてから、投稿数・トップ投稿者・リミットオーバー時刻・ポイントを更新する
- 対象場札の1人目および4人目以降の参加者は支払い履歴がない場合にレア度と同じポイントを消費し、2・3人目は0Pの支払い履歴を作成する
- 初投稿コストを消費した場合、現在の`event_id`と`event_card_id`を含む`trick_card_payments`へ履歴を作成し、`trick_event_cards.paid_points_total`へ加算する
- 投稿によるポイント消費は、所持ポイントが0P以下でも許可する
- その場札の1人目による初投稿は延長しない
- 2人目以降の初投稿は、参加順`k`に対して`max(5, 70 - 5k)`分延長する。2人目60分、3人目55分と5分ずつ逓減し、13人目以降は5分とする
- 2人目以降の延長はポイント消費の有無にかかわらず行い、同じプレイヤーのスコア更新では延長しない
- 大会終了1時間前以降の投稿では延長しない
- スタック数による制限時間ボーナスは設けない
- スコア投稿による即時ポイント還元は行わない
- 投稿成功時、次の給付金タイミングのフラグを有効化する
- ランクポイントは対象`event_card_id`に紐づく当該大会の有効投稿だけを集計し、参加者数`N`と順位`r`から`N - r + 1`、1位のみさらに1Rとして再計算する。スタック数と過去大会の同一`stage_id`記録は参照しない
- 同スコアは同順位グループとし、標準競技順位（例：1位・1位・3位）を順位`r`に使用する
- 投稿成功後の状態取得では、全場札の暫定ランクポイントを再集計し、`players.rank_points`の確定分と合算して返す

### 5.7 回収時のバックエンド処理

- 短周期ポーリングまたは期限切れ一括回収APIにより、回収条件を満たしている場札を回収する
- 回収対象は現在大会の`trick_event_cards`で`state = '_field'`かつ`limit_at`が現在時刻以前のカード、または大会終了時・即時回収時・管理者権限発動時の対象場札とする
- 回収時は対象の大会内場札を`_collected`、紐づく大会内`_stack`カードを`_trash`へ更新する。場札本体を`_trash`へ移してはならない
- 回収時の1位グループ全員を`trick_card_holders`へ共同ホルダーとして保存する。投稿者がいない場合はホルダー行を作成せず、ポイント還元とランクポイント確定を行わない
- ホルダーの有無にかかわらず`decks.stage_id`は変更・削除しない
- `_collected`は当該イベント中に山札へ戻さない。`_trash`だけが山札枯渇時の再シャッフル対象となる
- 回収時は最終順位の暫定ランクポイントを`players.rank_points`へ確定加算してから場札を回収済みにする。状態取得時の暫定集計対象から外れるため、表示合計を二重加算しない
- 回収処理は`event_id`と`event_card_id`を単位に冪等にする。すでに`_collected`の大会内カードに対して再度回収APIが呼ばれても、ホルダー、ポイント、ランクポイント、回収ログを二重作成・加算しない

#### 5.7.1 総還元ポイント計算

- 支払ポイント総数は`trick_event_cards.paid_points_total`または同じ`event_id`・`event_card_id`の`trick_card_payments`合計から取得する
- 基礎点 = `floor((stack_count + paid_points_total) / 5)`
- 難易度ボーナス = `difficulty * 基礎点`
- 総還元ポイント = `stack_count + paid_points_total + 難易度ボーナス`
- 投稿者が1人だけの場合は通常配分を行わず、その1人に `stack_count + paid_points_total` を固定還元する。この場合、難易度ボーナスは発生しない

#### 5.7.2 配分対象と配分計算

- 回収時点のランキングは、対象`event_card_id`へ`trick_event_records`で紐づく当該大会の各プレイヤーの有効な最高スコアで作成する
- 同スコアは同順位グループとして扱い、順位配分ポイントを同額にする
- 投稿者が2人以上の場合、最下位より上のプレイヤー数を数える
- 最下位より上のプレイヤー数が3人以上いる場合、タイを含む最下位のプレイヤーを順位配分対象から除外する
- 最下位より上のプレイヤー数が2人以下の場合、最下位タイを含めた投稿者全員を順位配分対象にする
- 配分は順位グループ単位で行い、以下の優先順位を満たす
    1. 総還元ポイントを使い切る
    2. 条件を満たす場合、最下位タイを除外する
    3. できるだけ多くのプレイヤーに1P以上配分する
    4. 1位、2位、3位、4位以下の差を可能な範囲で1P以上にする
    5. 同順位同配分を守るため順位配分できない端数は、順位配分とは別枠でテイカーに還元する
- テイカーへの端数還元は`reward_type = taker_remainder`として保存し、順位配分とは分離する
- 回収時の配分結果は`event_id`と`event_card_id`を含む`trick_collection_rewards`へ保存し、プレイヤーのポイントへ反映する

### 5.8 給付金処理

- 給付金処理は日本時間の毎時00分・30分を基準に行う
- 給付金タイミングでは、給付金フラグが有効で、かつ所持ポイントが5P以下のプレイヤーに1Pを付与する
- 所持ポイントが6P以上のプレイヤーには付与しない
- 給付金フラグは1種類のみで、場札0枚条件と行動条件で共通とする
- テイクまたはスコア投稿を行った場合、次の給付金タイミングに対してフラグを有効化する
- 給付金タイミングちょうどの行動で立ったフラグは、次回の給付金タイミングで消費する
- 場札が0枚であるかぎり、全プレイヤーの給付金フラグを有効として扱い、条件を満たすプレイヤーへ給付し続ける
- 給付金処理は`last_subsidy_paid_slot_at`等で冪等にし、同じ給付金タイミングで二重配布しない
- 大会単位の`last_subsidy_slot_at`も行ロック下で更新し、同じスロットを場札状態の変化後に再度処理しない

### 5.9 シミュレーションプレイヤーの行動モデル

- 全員に共通して、終了時に残るポイントと手札には効用を設定せず、テイク締切後のドロー・手札練習は行わない
- 各意思決定で、残り活動時間、テイク締切までの行動回数、将来のスタック数、予想投稿者数、腕前格差による予想順位、残ポイントの消費可能量を見積もる複数手先の予測モデルを使用する
- 予測上、終了までに消費しきれないポイントが多いほどドロー・初回投稿の価値を高く評価する。ただし、ランクPを減らしてまで無目的に消費する効用は与えない
- 全参加者は46時間59分59秒999999に活動セッション外でも締切直前テイクを1回だけ試行する。ただし固定クールダウンを含む通常のテイク条件は免除しない。この試行以外の最後の1時間の行動は各自の活動セッションに従う
- 所要時間のある行動は、開始から完了までが同一の活動セッション内かつ大会終了前に収まり、対象場札の既知の回収期限より前に完了できる場合だけ選択する
- 予約行動の対象が先に消滅した場合は同一時刻で意思決定を再予約し、失敗によって以後の行動連鎖を停止させない
- プレイヤーが所要時間のある行動中は別の意思決定を開始せず、複数行動を並行実行しない
- ドロー、テイクその他のUI操作時間は0分とし、同一時刻内で状態が変化する限り次の意思決定へ進む。シミュレーション上で時間を消費するのはミニゲームのプレイと手札練習だけとする
- テイク成功後90分間は、そのプレイヤーの次のテイクを行動候補から除外する。場札の投稿・回収状態による早期解除は行わない
- 初回投稿のミニゲーム時間はパーソナリティにかかわらず10〜60分とする。難易度1〜5の最低時間は10・15・20・25・30分とし、意欲係数による個人差を加える。パーソナリティは投稿先と行動目的の差にだけ使用し、ミニゲーム自体の機械的な所要時間とは分離する
- プレイヤー×場札ごとに、挑戦回数、更新回数、累計通常プレイ時間、直前の更新所要時間を保持する
- 更新は現在スコアより上の最も近いスコアを目標とし、目標スコア、自分の腕前係数、累計プレイ時間、練習効果から必要追加時間を逆算する。更新回数ごとに探索コストを加算し、次の更新時間は同じプレイヤー・場札の直前更新より少なくとも5分長くする
- 各プレイヤーには大会を通じて一定の腕前係数`0.55〜1.45`を割り当て、`(累計通常プレイ時間 + 逓減後の手札練習時間) × 腕前係数`をスコア評価値とする
- 手札練習はテイクするまで回数上限なしで累積できるが、有効練習分は`60 × log(1 + 実練習分 / 60)`として長時間ほど追加効果を逓減させる
- 場札への初回投稿は、予想ランクP、予想還元P、参加料、必要プレイ時間、テイカーの推定練習優位を合成した期待効用とパーソナリティ別の参加傾向から参加確率を求める
- 正統派：複数手先の予測ランクP、行動時間、終了時に無価値となるポイントを評価し、投稿・更新・練習・ドロー・テイクからランクP最大化に有利な行動を選ぶ
- 投稿優先派：未投稿の場札がある間は、短時間で投稿できる場札を優先し、できるだけ多くのゲームからランクPを集める。現在の全場札へ投稿済みの場合は正統派と同じ予測行動を取る
- ネガティブ派：基本判断は正統派と同じだが、まず練習用として現在のテイク必要枚数を満たす手札を確保し、練習成果をテイク締切前に場へ出せる見込みがある場合は、ランクP以外の練習効用も高く評価する。総合順位は目的にしない
- スタック派：ランクPを目的にせず、手札14枚を目標にドローを続け、巨大スタックのテイクを優先する。テイク締切後は余剰ポイントを場札への投稿に使う
- 場札が0枚で、活動中のプレイヤーのうち誰か1人がテイクすれば循環を再開できる場合は、手札が最も多い1人が合意担当となり、パーソナリティよりテイクを優先する
- 初投稿のない場札はテイクから90分で自然回収されるため、合意による強制初投稿は行わない
- 場札のランクPは参加者数`N`を基準に`N - 順位 + 1`を付与し、1位にはさらに1Rを加算する。スタック数は使用しない

## 6. Laravel API設計

### 6.1 基本方針

- Laravel側のイベント専用APIは`laravel/app/Http/Controllers/TrickController.php`へ定義する
- Next.jsからは既存の`/api/server/[...query].js`プロキシ経由でLaravel APIを呼び出す。例：Laravel pathが`/api/tricks/state`の場合、フロントエンドからは`/api/server/tricks/state`を呼ぶ
- 認証ユーザーIDはNextAuthのセッションを基準にし、クライアントから送られた`userId`だけを信用しない
- 全APIはJSONを返す。失敗時はHTTPステータスと`message`を返す

### 6.2 取得系API

| Method | Laravel path                        | 用途              | 主なレスポンス                                             |
|--------|-------------------------------------|-----------------|-----------------------------------------------------|
| GET    | `/api/tricks/tournament`            | 大会情報取得          | `event_id`、`start_at`、`end_at`、`server_now`、`debug` |
| GET    | `/api/tricks/state`                 | 画面全体のスナップショット取得 | 大会情報、確定・暫定・合計ランクPと`last_take_at`・`next_take_at`を含む参加者、場札、自分の手札、山札枚数、捨て札枚数、ログ |
| GET    | `/api/tricks/players`               | ダッシュボード取得       | 参加者一覧、確定ランクP、場札の暫定ランクP、両者の合計                     |
| GET    | `/api/tricks/hand`                  | 自分の手札取得         | 手札カード一覧                                             |
| GET    | `/api/tricks/field`                 | 場札取得            | 場札カード一覧                                             |
| GET    | `/api/tricks/collected`             | 回収カード取得         | 指定`event_id`の回収カード、ホルダー一覧、再登場可否、大会別ランキング              |
| GET    | `/api/tricks/cards/{deckId}/scores` | 場札ランキング取得       | 現在の`event_id`・`event_card_id`に限定した有効投稿ランキング、初投稿コスト支払い済みフラグ |
| GET    | `/api/tricks/logs`                  | ログ取得            | ドローを除外した最新100件の表示用ログ                               |

`/api/tricks/state`はポーリングの中心APIとする。初期値は2-5秒間隔を想定し、投稿直後・テイク直後などは即時再取得する。

- 取得系APIは状態変更を行わない。期限回収、給付、大会終了処理はmaintenance経路または運用ジョブで実行し、処理後に最新状態を再取得する

### 6.3 更新系API

| Method | Laravel path                               | 用途       | 主な処理                                             |
|--------|--------------------------------------------|----------|--------------------------------------------------|
| POST   | `/api/tricks/join`                         | 大会参加     | `players`作成、参加者本人へ5P付与、既存参加者へ後発参加ボーナス付与          |

| POST   | `/api/tricks/cards/{deckId}/take`          | テイク      | 条件検証、場札化、スタック化、給付金フラグ有効化                         |
| POST   | `/api/tricks/cards/{deckId}/collect`       | 管理回収     | 管理者・運用ジョブだけが共通回収処理を実行                               |
| POST   | `/api/tricks/cards/{deckId}/debug-collect` | デバッグ回収   | デバッグ・テスト大会で管理者またはテスト署名がある場合だけ即時回収                 |
| POST   | `/api/tricks/maintenance/collect-expired`  | 期限切れ一括回収 | ポーリングまたは管理操作で期限切れカードを回収                          |
| POST   | `/api/tricks/maintenance/subsidy`          | 給付金処理    | 現在の日本時間スロットに対する給付金を冪等に配布                         |

| POST   | `/api/tricks/debug/time/freeze`            | 時刻停止     | 現在の大会時刻を`debug_now`へ固定                              |
| POST   | `/api/tricks/debug/time/set`               | 時刻設定     | 指定時刻へ変更                                           |
| POST   | `/api/tricks/debug/time/advance`           | 時間経過     | 秒・分・時間単位で大会時刻を進め、必要に応じてmaintenance処理を実行          |
| POST   | `/api/tricks/debug/time/reset`             | 時刻復帰     | 制御時計を解除して実時刻へ戻す                                  |

- `debug/time/set`は大会処理開始後の時刻を過去へ戻す用途には使わない。テストの巻き戻しはイベントを作り直して行う
- `debug/time/advance`は移動区間内の期限、00/30分給付、大会終了を時系列順に処理し、大きな時間移動でも途中スロットを飛ばさない

### 6.4 投稿APIとの連携

- 実際のスコア投稿は既存の`next/components/modal/RecordForm.js`から`/api/server/post`へ送る
- 投稿フォームには対象カードの専用`stage_id`を`stage_id`として渡す
- 投稿モーダルのステージ名は、ローカライズ辞書に存在しない場合、`stages.stage_name`またはカードタイトル由来の名称を表示する
- 汎用記録の作成・編集・削除処理は、対象`stage_id`が開催中の大会内カードに一致する場合、イベント用ドメインサービスを同じサーバー処理内で呼び出す
- クライアントから投稿成功後のイベント更新APIを追加で呼ばせない。記録だけ成功してイベント更新が欠落する状態や、更新API再送による二重延長を許さない
- `records`へのカラム追加は行わず、作成済み`record_id`を`trick_event_records`へ紐付ける

### 6.5 デバッグ・テスト認証

- 通常操作の本人IDはNextAuthセッションを正本とし、Nextプロキシが内部署名付きでLaravelへ渡す
- Playwrightの複数プレイヤーテストに限り、`test_mode`大会と有効なテスト署名の組み合わせでユーザー偽装を許可する。本番・通常デバッグ大会では無効にする
- 即時回収、時刻操作、fixture作成・削除は管理者またはテスト署名を必須とする
- 管理操作ではNextAuthのロールも署名対象に含め、Laravel側で管理者ロールを検証する
- `TRICKS_DEBUG`等の設定が欠落した場合はデバッグ無効を既定値とする

### 6.6 エラー仕様

| ステータス | 用途                                     |
|-------|----------------------------------------|
| 400   | リクエスト形式不正                              |
| 401   | 未ログイン                                  |
| 403   | 大会時間外、未参加、権限なし、デバッグ無効                  |
| 404   | 対象カードなし                                |
| 409   | 状態競合。すでに回収済み、手札でない、場札数上限、固定クールダウン中、初投稿コスト支払い競合など |
| 422   | 入力値は正しいがルール条件を満たさない                    |
| 500   | 想定外エラー                                 |

- テイクAPIが固定クールダウン中のため409を返す場合は、レスポンスに`next_take_at = last_take_at + 90分`を含める

### 7.1 Playwright UI/APIテスト

- 本サブプロジェクト専用のPlaywright設定は`next/pages/limited/tricks/playwright.config.cjs`、テスト本体は`next/pages/limited/tricks/tests/*.cjs`に配置する

- 各テストの`finally`で対象`event_id`配下だけを削除し、readbackで残存0件を確認する。既存の大会データを前提にしたり変更したりしない

npx playwright test -c pages/limited/tricks/playwright.config.cjs

docker compose up -d

docker compose exec -d next yarn dev -H 0.0.0.0

docker compose exec -e TRICKS_E2E_CHROME_EXECUTABLE=/usr/bin/chromium-browser next npx playwright test -c pages/limited/tricks/playwright.config.cjs

- `next`コンテナがAlpine Linuxの場合、Playwright同梱のUbuntu/glibc向けChromiumは実行できないため、AlpineのシステムChromiumを利用する。この場合は`apk add chromium`等で導入し、`TRICKS_E2E_CHROME_EXECUTABLE=/usr/bin/chromium-browser`を指定して実行する。Dockerイメージ側でChromiumを常設した場合は、`apk add chromium`の手順は省略できる

```bash
TRICKS_E2E_CHROME_EXECUTABLE=/usr/bin/chromium-browser npx playwright test -c pages/limited/tricks/playwright.config.cjs
```

- 現在のUI/APIテストでは以下を確認する
    - `/api/server/tricks/state`がNextプロキシ経由でイベント状態スナップショットを返す
    - 参加時に5P付与され、自動ドローされない
    - 後発参加ボーナスが既存参加者のみに付与される
    - ポイント0P以下ではドローできない
    - テイク時に90分タイマーが開始し、1人目の初投稿では延長されない
    - 2・3人目の初投稿コストは0P、4人目以降はレア度分となる
    - 2人目以降の初投稿はコストの有無にかかわらず60分から5分ずつ逓減して延長され、スコア更新では延長されない
    - スコア投稿による即時ポイント還元が発生しない
    - 参加者数`N`と順位`r`から`N - r + 1`、1位のみさらに1Rとして算出され、スタック数を変えてもランクPが変わらない
    - 同じプレイヤーのテイク成功間隔が90分未満にならず、投稿・回収によって固定クールダウンが解除・延長されない
    - 投稿・更新直後に暫定ランクPが変動し、回収時に確定分へ移しても表示合計が二重加算されない
    - 回収時の総還元ポイント、同順位同配分、最下位除外条件、テイカー端数還元が正しく処理される
    - 給付金タイミングで、フラグ有効かつ5P以下のプレイヤーだけに1P給付される
    - 投稿者0人の回収カードにはホルダーが作成されず、同じイベント中は再登場せず、次回イベントでは既存`stage_id`のまま山札へ戻る
    - ホルダーありの回収カードは`_held`となり、次回以降のイベントの山札へ入らない
    - 同じカードと`stage_id`を次回イベントで再利用しても、前回大会の記録、参加順、支払い、ランクP、還元結果が混入しない
    - 山札枯渇時は当該大会の`_trash`だけを`_deck`へ戻し、`_collected`は戻さない
    - 同じ場札を複数回回収してもポイントと回収ログが重複しない
    - 大会終了後は手札・山札・捨て札を描画せず、その大会の回収カード一覧とホルダー有無を表示する
    - `/limited/tricks`を開いたとき、Phaserのcanvasが表示され、描画済みピクセルを持つ
    - 同点順位が標準競技順位（1位・1位・3位）となる
