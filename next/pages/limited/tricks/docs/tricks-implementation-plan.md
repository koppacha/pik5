## 2. 実装差分の全体像

### 2.1 大会・参加・ポイント

- `players`を大会単位へ分離し、`event_id + name`を一意にする
- `draw_points`という物理名を互換維持する場合も、API/UI上は「ポイント（P）」へ統一する
- 新規参加は5P、手札0枚とし、自動3枚ドローを廃止する
- 既存参加者全員へ後発参加ボーナス1Pを一度だけ加算する
- 同じ参加要求の再送、同時参加、別大会の同名プレイヤーを考慮して冪等化する
- 大会終了時の勝敗・表示順を合計ランクPだけで決める

### 2.2 カード本体と大会内カード状態

- `decks`をイベントをまたぐカード本体へ限定し、`stage_id`を永続化する
- `trick_event_cards`を追加し、山札・手札・場札・スタック・捨て札・回収済みを大会単位で管理する
- 大会開始時に、直前大会のホルダーなし回収カードを優先して含め、残りを他の`_eligible`カードから補って200枚を確保する。合計が足りなければ初期化を失敗させる
- 回収された場札本体は同大会中に循環へ戻さず、スタックカードだけを`_trash`へ移す
- 山札枯渇時は同大会の`_trash`だけを戻し、`_collected`を混ぜない
- ホルダーありはカード本体を`_held`として以後の大会から除外し、ホルダーなしおよび大会終了時の未獲得カードは`_eligible`へ戻す
- 既存の100枚ダミーseederを200枚・新テーブル構造へ更新する

### 2.3 ドロー

- 0P以下を拒否し、成功時だけ1Pを消費する
- ★2以上排出率を経過時間`t`に対する`min(100, 10 × 10^(t / 46))%`へ変更する
- ★2以上の比率`6:3:0.9:0.1`と難易度抽選・欠損難易度補正を実装する
- 抽選、山札再構成、カード取得、ポイント更新、手札数同期を同一トランザクションと行ロックで処理する
- UIは未参加、0P以下、大会時間外、処理中にはドローを非活性化する

### 2.4 テイク

- 必要手札数を`3 + テイク直前の場札数`へ変更する
- 場札上限を`min(max(1, 累計参加者数 - 1), 16)`へ変更する
- `players.last_take_at`を追加し、成功時から90分のクールダウンを適用する。案Aの全場札1位解除と案Bの終了150分前以降の免除は共通判定に集約する
- `limit_at`はテイク成功時に90分後を設定し、初投稿待ちnullを廃止する
- 未発行時だけ`stage_id`を採番し、再登場時は既存値を使う
- 選択外手札を大会内スタックへ移し、親`event_card_id`を保存する
- APIは競合理由を区別し、クールダウン409には`next_take_at`を返す
- UIは必要枚数、場札上限、締切、クールダウンを事前表示し、確認ダイアログ後にAPIを呼ぶ
- 現行の成功前アニメーションを改め、API成功を受けてから移動演出し、失敗時に見た目だけ成功しないようにする

### 2.5 投稿・参加順・時間延長・ポイント消費

- `trick_event_records`で汎用`records`を大会内カードへ明示的に紐付ける
- `trick_card_payments`でプレイヤー×大会内カードの初投稿履歴を永続化する
- 1人目と4人目以降はレア度分、2・3人目は0Pの支払い履歴を作る
- 0P以下でも投稿を許可し、ポイントは負数まで減算可能にする
- 1人目は延長なし、2人目以降は`max(5, 70 - 5k)`分延長し、更新と終了1時間前以降は延長しない
- 投稿削除・再投稿でも支払いを失わず、二重消費・二重延長を防ぐ
- 投稿成功後の別APIをクライアントが任意に呼ぶ現構造を廃止し、記録作成とイベント副作用をサーバー側で確実に連携する
- 記録作成・編集・削除のすべてで有効最高スコアと暫定ランクPを再計算する
- 新着記録・ピックアップ動画からイベント用ステージを除外する

### 2.6 ランクP

- 場札ごとに参加者数`N`と順位`r`から`N - r + 1`、1位だけ+1Rを算出する
- 同点は標準競技順位（例：1位・1位・3位）として同じランクPを付与する
- スタック数による加点と人数不足ボーナスを完全に削除する
- `players.rank_points`は回収済みの確定分だけを保持し、場札の暫定分は問い合わせ時に大会内投稿から集計する
- state/players APIは`confirmed_rank_points`、`provisional_rank_points`、`total_rank_points`を返す
- 回収時に暫定分を確定へ一度だけ移し、場札集計から外して二重加算を防ぐ
- ダッシュボードは合計R降順、同点時は安定した規則で並べ替える

### 2.7 回収・還元・ホルダー

- `trick_collection_rewards`へ配分結果を保存し、回収の再実行でも再加算しない
- 支払総数、基礎点、難易度ボーナスから総還元Pを算出する
- 単独投稿は`stack_count + paid_points_total`だけを固定還元する
- 複数投稿は同順位グループ、最下位除外条件、順位差の優先順位、テイカー端数還元を独立した純粋関数として実装する
- `trick_card_holders`へ1位グループ全員を共同ホルダーとして保存する
- 投稿者0人では還元・R・ホルダーを作らない
- 期限、大会終了、デバッグ即時回収、管理者回収を同じ回収サービスへ集約する
- 大会終了時は期限にかかわらず全場札を回収する。大会内カード履歴は既存状態のまま保持し、カード本体をホルダーあり`_held`、それ以外`_eligible`へ遷移させる
- `/tricks/collected`を追加し、過去大会の回収カード・ホルダー・再登場可否・大会別ランキングを返す

### 2.8 給付金

- `subsidy_flag`、`subsidy_flag_slot_at`、`last_subsidy_paid_slot_at`を大会別プレイヤーへ追加する
- JST毎時00分・30分のスロットを明示的に計算する
- テイクまたは投稿で次スロットのフラグを立て、時刻境界ちょうどの行動を次回扱いにする
- 場札0枚中は全員を継続対象とし、5P以下だけ1P付与する
- 同スロットの多重実行を一意制約・行ロック・履歴で防止する
- 取得系APIはread-onlyとし、maintenance APIと運用cronの責務を分離する

### 2.9 API認証・競合・監査

- Next APIプロキシがNextAuthセッションのユーザーIDを内部署名付きヘッダーでLaravelへ渡す
- LaravelはクライアントJSON/queryの`userId`を本人確認に使用しない
- 未認証の参照可否と、参加・ドロー・テイク・投稿・デバッグ操作の権限をルートごとに明示する
- 大会ID、event_card_id、ポイント差分、状態遷移を`limit_logs`へ保存する
- 監査ログにはドローも保存するが、画面表示用ログAPIではドローを除外する
- 通常collectとdebug-collectを分離し、通常ユーザーが任意カードを即時回収できないようにする
- 全更新系で大会状態と対象行をロックし、409/422/403を仕様どおり使い分ける

### 2.10 UI

- `TricksLayeredGame.js`を`next/components/tricks/`へ移し、未使用の旧`TricksGame.js`と責務を整理する
- P、手札数、確定R、暫定R、合計R、次回テイク可能時刻をダッシュボードへ反映する
- 捨て札枚数を追加し、山札・手札・捨て札は大会終了後に非表示にする
- 場札カードへ初投稿コスト、スタック数、期限、テイカーを表示する
- 場札詳細へ大会内ランキング、現在の参加順／支払済み状態、投稿コスト説明を表示する
- 大会終了後は通常の場札とは別の回収カード一覧を表示し、投稿ボタンを無効化する
- 回収カードには共同ホルダー全員または「ホルダーなし」、再登場可否を表示する
- デバッグ時だけカード回収ボタンと時間操作パネルを表示する
- 練習を状態変更のない行為として扱う場合、手札詳細からルールを常時閲覧できるようにする

## 3. 既存コードで検出した不具合

1. 通常`POST /cards/{id}/collect`とdebug-collectが同じ無条件処理に接続され、任意の利用者が期限前に即時回収できる
2. Nextプロキシはセッションを取得するがLaravelへ本人IDを注入せず、Laravelはbody/queryの任意`userId`を信用するため、他人として操作できる
3. `recordPosted`は`record_id`や投稿者を検証せず、同じ要求の再送で15分延長を繰り返せる
4. 汎用記録作成とイベント副作用が別リクエストで、後者失敗・未呼び出し時に記録だけが残り状態が不整合になる
5. 大会終了時に全場札を強制回収せず、state APIが未回収`_field`を回収済みと同列に返す
6. `recalculateRankPoints()`が大会を絞らず全`players`を0へ戻し、別大会を破壊しうる
7. ランキングが同点を同順位にせず、作成順で異なる連番順位を付ける
8. ランキングが`stage_id`だけで全期間の記録を集計し、同じカードの次回大会へ過去記録が混入する
9. state GETが回収という書き込みを行う一方、クライアントも5秒ごとに回収POSTを実行し、処理と再取得が重複する
10. SWRが1秒ごとに画面全体を更新し、設計の2〜5秒より短く、状態不変時にもReact/Phaser再描画を誘発する
11. スタック数6以上の場札が1枚でもあるとFX canvasの`requestAnimationFrame`が常時継続し、低負荷要件に反する
12. ドロー・テイク演出がAPI成功前に始まり、失敗しても一時的に成功したように見える
13. `TRICKS_DEBUG`の既定値がtrueで、本番設定漏れ時にデバッグ機能が有効になる
14. stateレスポンスにある`trash_count`をフロント正規化で捨て、UIにも表示していない
15. 既存ダミーseederは100枚しか作らず、全プレイヤーを99Pへ更新するため、新仕様の初期状態とテスト隔離を壊す
16. 既存E2Eは旧15分延長・投稿即時DP・旧単一テーブル構造を前提とし、新仕様に対して誤った期待値を検証する
17. 現行ログAPIは監査ログと表示ログの区別がなく、ルール上は非表示であるドローが画面ログへ混入しうる
18. 現行シミュレーターは選んだカードの難易度をドロー時に上書きしており、山札内カードの固有難易度と欠損難易度補正を使うシステム仕様と一致しない

## 5. Playwright向けデバッグ機能

### 5.1 イベント単位の制御時計

- 本番は実時刻、debug/testイベントだけはDB上の`debug_now`を参照する`TrickClock`へ時刻取得を集約する
- debug APIで`freeze`、指定時刻へ`set`、秒／分／時間単位の`advance`、実時刻へ`reset`を提供する
- 時刻変更後に期限回収・給付金処理を明示実行でき、API応答へ処理件数と現在時刻を返す
- 大会処理開始後の過去時刻への巻き戻しは禁止し、大きな`advance`では途中の期限・給付スロット・大会終了を時系列順に処理する
- これにより90分、47時間締切、48時間終了、00/30分給付を自然待機せず検証する
- テストごとに一意なevent_idと時計を使い、並列実行しても他テストや既存ローカル大会を動かさない

### 5.2 テストfixture API/CLI

- debug/test限定で大会作成、200枚初期化、複数プレイヤー作成、ポイント・手札・場札の準備を行うfixture経路を用意する
- 内部DB直接INSERTを最小化し、通常のドメインサービスを通してfixtureを作る
- teardownはevent_id配下だけを外部キー順に削除し、対象件数をreadbackして残存0を確認する
- 乱数seedを指定できるようにし、レア度補正テストを再現可能にする

### 5.3 観測機能

- debug stateへサーバー時刻、次回給付スロット、各プレイヤーの次回テイク時刻、場札の参加順・延長履歴・支払総数を返す
- ブラウザ側へGameObject数、DOMカード数、稼働中Tween/timer/RAF数、state取得回数、実再描画回数を公開する読み取り専用debug snapshotを用意する
- 読み取り専用debug snapshotは`window.__TRICKS_DEBUG_SNAPSHOT__()`から取得でき、通常UI操作やゲーム状態の変更機能は持たせない
- Playwrightで初期値と一定時間後を比較し、操作なしでオブジェクトやRAFが増加・常時稼働しないことを検証する

## 7. 2026-09-07 テイククールダウン案A+B採用計画

### 7.1 影響調査

- テイク可否の正本は`TrickGameService`、状態APIとUIの事前判定は`TrickStateService`が返す`next_take_at`であり、両者を共通サービスへ集約する
- 案Aは成立後に順位が変わっても次のテイクまで解除を維持するため、`players.take_cooldown_released_for`へ解除対象の`last_take_at`を保存する
- 案Aの成立契機は記録投稿・更新・削除と場札回収である。順位と場札構成の変化後に全クールダウン中プレイヤーを再評価する
- 案Bは大会終了150分前から既存クールダウンを免除する。大会終了1時間前のテイク締切、必要手札、動的場札上限、手札消費は変更しない
- テイク、投稿、回収はいずれも大会行を先にロックする既存順序を維持し、同時更新で案A判定と次回テイクが食い違わないようにする

### 7.2 実装順序

1. 案Aの解除対象テイク時刻を保存するnullable列とモデルcastを追加する
2. 90分、案Aの永続解除、案Bの終了150分前境界を評価する共通クールダウンサービスを追加する
3. 記録・削除・回収後に、場札2枚以上、他テイカーあり、全場札1位を満たすプレイヤーの解除状態を保存する
4. テイクAPIと状態APIを共通判定へ切り替え、テイク成功時に前周期の解除を消去する
5. 単体テスト、投稿からの案A成立テスト、テイク回帰テスト、全Tricksテスト、PlaywrightのUI事前判定を実行する

### 7.3 完了条件

- 案Aは同率1位を含み、条件成立後の順位変動でも解除が維持され、次のテイク成功後には再び条件成立が必要になる

- クールダウン以外の必要手札、場札上限、ポイント・スタック処理に回帰がない
