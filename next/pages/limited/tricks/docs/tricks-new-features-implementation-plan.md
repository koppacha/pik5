# 新機能の実装差分と実装計画

調査日: 2026-09-20

## 1. 調査対象

- 正式ルール: `docs/tricks-rules.md`
- UI・API設計: `docs/tricks-system.md`
- シミュレーション仕様: `docs/tricks-simulation.md`
- Laravel: `TrickRuleCalculator`、`TrickGameService`、`TrickSubsidyService`、`TrickCollectionService`、`TrickRecordService`、`TrickStateService`

## 2. 結論

今回の追加仕様のうち、成功テイク数からレベルを求める処理と、状態APIでのレベル・テイクコスト返却は実装済みである。一方、次の機能は未実装または旧仕様のままである。

| 機能 | 現状 | 判定 |
|---|---|---|
| C案の全額還元式 | `totalReward()`は3/5控除と難易度ボーナスを使う旧式。単独投稿も全額還元ではない | 未実装 |
| 新しい順位配分 | `TrickRewardDistributor`は旧「配分対象拡大・最下位除外・順位差」方式 | 未実装 |
| 残高税 | 給付後の閾値判定、1P徴収、監査ログがない | 未実装 |
| 大会単位Pot | DB列・モデル・状態APIがなく、返却費も消費されるだけ | 未実装 |
| Pot付き回収 | 回収処理がPotをロック・加算・消費しない | 未実装 |
| 暫定還元へのPot反映 | 暫定還元は旧`totalReward()`だけで算出 | 未実装 |
| 手札上限 | 上限計算、API返却、サーバー側ドロー拒否、UI非活性化がない | 未実装 |
| 大会情報の2カラム・2人分幅 | 現在は最小幅156pxの1カラム | 未実装 |
| Pot、山札、捨て札の大会情報表示 | Potなし。山札・捨て札はコマンド領域に表示 | 未実装 |
| 課税対象残高の緑表示 | 給付対象はピンク表示するが課税対象判定・表示はない | 未実装 |
| 手札の現在数／上限表示 | 現在数だけ表示 | 未実装 |
| 場札右下の暫定還元総額 | 現在は`stack_count`を表示 | 未実装 |
| 場札ポップアップの指定ヘッダー | 情報は概ね存在するが、順序・文言・スタックが不足 | 一部実装 |

## 3. 実装方針

### 3.1 ルール計算を先に確定する

`TrickRuleCalculator`へ次を追加・変更する。

- `handLimit(takeCount) = (takeLevel(takeCount) + 2) * 3`
- `balanceTaxThreshold(takeCount) = (takeLevel(takeCount) + 2) * 5`
- 総還元を投稿者1人以上なら`stack_count + paid_points_total + pot_points`、0人なら0とする
- 難易度引数を総還元計算から外す

`TrickRewardDistributor`はルール仕様書4.4.2〜4.4.4どおり、参加人数別基底配分、下位側からの減額、1P単位の循環加算、同順位均等化、最下位端数配分へ置き換える。旧アルゴリズムの`eligibleGroups()`と`gapsAreValid()`を前提にしない。

### 3.2 Potの永続化と原子的更新

`trick_events`へ非負整数の`pot_points`（既定値0）を追加し、`TrickEvent`と大会状態APIから参照できるようにする。

- 手札返却: プレイヤーから減算した1Pを、同一トランザクション内でイベント行をロックしてPotへ加算する
- 残高税: 給付処理後、対象プレイヤー全員から1Pずつ減算し、徴収合計をPotへ一括加算する
- 回収: イベント行・場札をロックし、投稿者がいる場合だけ現在Pot全額を総還元へ加え、配分結果の保存と同時にPotを0にする
- 投稿者0人の回収: Potを変更しない
- 冪等再実行: 回収済みカードではPotを再消費しない

監査ログには少なくとも、徴収スロット、対象プレイヤー、徴収前後残高、徴収合計、Pot前後値を秘密情報を含めず保存する。公開ログへの残高税表示は今回のUI要件にないため追加しない。

### 3.3 残高税

`TrickSubsidyService::processSlot()`で給付を完了した後に、同じイベント・プレイヤーロックのまま次を行う。

1. 各プレイヤーの成功テイク数から閾値`(L + 2) * 5`を算出する
2. 給付後残高が閾値を超えるプレイヤーから1P徴収する
3. 徴収合計をPotへ加算する
4. 既存の`last_subsidy_slot_at`によるスロット冪等性の範囲内で完了させる

状態APIの各プレイヤーへ`balance_tax_threshold`と`balance_tax_eligible`を返す。UIは`balance_tax_eligible`が真のプレイヤーだけ残ポイント数を緑色にし、給付対象のピンク表示とは役割を分ける。

### 3.4 手札上限

状態APIの各プレイヤーへ`hand_limit`を返す。ドロー処理ではプレイヤーと現在手札をロックした後、実数が上限以上なら422で拒否する。`players.card_count`だけを信頼せず、`trick_event_cards`の実数で再検証する。

フロントの`tricksOperationState()`でも`handCount >= handLimit`をドロー不可理由に追加する。プレイヤーカードは`手札 {card_count} / {hand_limit}`と表示する。これによりUI先行の非活性化と、競合時にも破れないサーバー側制約を両立する。

### 3.5 暫定還元とPot対象の扱い

Potは「実際に先に回収された、投稿者がいる場札」が消費するため、複数場札へ同時にPotを足すと見かけ上の二重計上になる。状態スナップショットでは次の規則で暫定対象を一意にする。

- 投稿者がいる未回収場札を`limit_at`昇順、同値なら`event_card_id`昇順に並べ、先頭だけを「暫定Pot対象」とする
- 管理回収などで順序が変わり得るため、実際の配分は回収トランザクション時のPotを正とする
- 各場札に`provisional_total_reward`と`provisional_pot_points`を返す
- ランキング各行の`provisional_reward_points`も、暫定Pot対象カードだけPot込みで再計算する

場札右下は`stack_count`ではなく`provisional_total_reward`を表示する。投稿者0人では総還元0Pなので0を表示する。

### 3.6 UIレイアウト

大会情報カードはプレイヤーカード2枚分（現状基準で`132px * 2 + gap 8px`以上）の幅を確保し、本文を2カラムにする。

- 常時表示: 場札上限、回収カード総数、大会残り時間、山札、捨て札
- 条件表示: 次回給付、Pot（1P以上の場合だけ）
- コマンド領域: 山札・捨て札表示を削除し、操作不可理由は残す
- プレイヤー情報: `手札 現在数 / 上限`、課税対象の残ポイント数を緑表示
- 場札右下: 暫定還元ポイント数
- 場札ポップアップヘッダー: `スタック X / 支払い総額 XP / 参加者 X人 / あなたの投稿コスト XP`

スマートフォンでは大会情報カード自体を縮めず、既存のヘッダー内横スクロールで破綻を避ける。追加の常時描画ループは作らず、既存state更新だけで表示を更新する。

## 4. 実装順

1. `TrickRuleCalculator`と`TrickRewardDistributor`を新仕様へ変更し、unit testで数式を固定する
2. `trick_events.pot_points`のmigrationとモデル対応を追加する
3. 手札返却、給付後残高税、回収の各トランザクションへPot処理を追加する
4. ドローAPIへ手札上限のサーバー側制約を追加する
5. `TrickStateService`へPot、税閾値・対象状態、手札上限、暫定総還元を追加する
6. HUD、コマンド領域、場札、ポップアップを指定UIへ変更する
7. Laravel test、Playwright test、実ブラウザ表示確認を行う

## 5. テスト計画

### Laravel unit test

- レベル境界`T=0,1,4,9`に対する手札上限`6,9,12,15`と税閾値`10,15,20,25`
- `Q=S+C+P`、投稿者0人の`Q=0`、難易度非依存
- 参加者1〜6人の基底配分、`Q<N+3`、循環加算、同順位、最下位端数

### Laravel feature test

- 手札が上限未満ならドロー成功、同値以上なら422、ポイントとカード状態が不変
- 給付後に閾値超過だけ1P徴収、閾値同値は非徴収、同じスロットの再実行で二重徴収なし
- 返却費がPotへ入り、投稿者あり回収で全額消費、投稿者なし回収では持ち越す
- 同時または再実行された回収でPot・還元が二重反映されない
- 暫定Pot対象と実回収結果、Pot消費後のstate再計算
- 既存の投稿費・任意延長費が`paid_points_total`に一度だけ含まれる

### Playwright

- 大会情報が2人分幅・2カラムで、Pot 0P時は非表示、1P以上で表示される
- 山札・捨て札が大会情報へ移り、コマンド領域には残っていない
- 課税対象者の残ポイント数だけが緑色になる
- 手札表示が`現在 / 上限`になり、上限到達時のドローボタンが非活性
- 場札右下とポップアップヘッダーがAPI値に一致する
- 横幅1024px以上と狭幅の両方でヘッダー横スクロール、場札、手札、ログ操作が破綻しない

### 負荷・破棄確認

- stateポーリング1回につき暫定Pot対象と還元配分を一括取得し、場札ごとのN+1 queryを発生させない
- Reactのstate更新のみで表示し、Phaserの常時再描画や追加タイマーを導入しない
- 画面遷移後に既存ポーリング、タイマー、DOMオブジェクトが残らないことを確認する

## 6. 完了条件

- 正式ルール、状態API、回収結果、画面表示の総還元値が一致する
- Potの生成元と消費先を監査ログから追跡でき、二重生成・二重消費がない
- 手札上限がUIとAPIの両方で強制される
- 指定された大会情報・プレイヤー情報・場札・ポップアップ表示をPlaywrightで確認できる
- Laravelの対象unit/feature test、Next.js lint、Playwrightの対象specが成功する
